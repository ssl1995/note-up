# Kafka消息有序性 - 面试完整指南

## 一、核心结论（30秒版）

> **Kafka只能保证Partition内有序，不能保证Topic全局有序。**

所以"保证消息有序" = **让需要有序的消息进入同一个Partition**

---

## 二、Kafka分区流入规则（必背）

| 条件 | 结果 |
|------|------|
| 指定了Partition | 发送到指定Partition |
| 没指定Partition，但指定了Key | 按Key的Hash取模决定Partition |
| 都没指定 | 轮询（Round-Robin）写入 |

**关键代码：**
```java
// 默认分区器
partition = Math.abs(key.hashCode()) % numPartitions
```

---

## 三、保证有序的方案（由简到繁）

### 方案1：单Partition（最简单）
```
Topic只建1个Partition
```
- ✅ 全局有序
- ❌ 吞吐量受限，无法水平扩展

### 方案2：业务Key分区（最常用）
```
订单消息 → Key=orderId
用户消息 → Key=userId
```
- ✅ 同一业务实体有序
- ✅ 可并行处理不同实体
- ❌ 热点问题（大Key）

### 方案3：自定义分区器（高级）
解决热点问题，用**哈希槽**或**一致性Hash**

---

## 四、哈希槽 vs 一致性Hash（重点）

### 4.1 哈希槽（Hash Slot）— Redis Cluster方案

```
┌─────────────────────────────────────┐
│  固定16384个槽位（0-16383）           │
│                                     │
│  节点A: 槽 0-5000                   │
│  节点B: 槽 5001-10000               │
│  节点C: 槽 10001-16383              │
└─────────────────────────────────────┘

Key → CRC16(key) % 16384 → 确定槽位 → 确定节点
```

**优点：**
- 扩容时只需迁移部分槽位
- 客户端可缓存槽位映射表

**Kafka应用：**
```java
// 自定义分区器：将用户ID映射到固定槽位
int slot = CRC16(userId) % 16384;
int partition = slotToPartitionMap[slot];
```

---

### 4.2 一致性Hash（Consistent Hashing）

```
传统Hash问题：节点变化 → 大量数据重新映射

一致性Hash解决：
┌─────────────────────────────────────┐
│  哈希环（0 ~ 2^32-1）               │
│                                     │
│      节点A ●                        │
│           \                         │
│            \    数据按顺时针找节点    │
│      节点C ●——→● 节点B              │
│                                     │
│  新增节点D：只影响D逆时针方向的数据   │
└─────────────────────────────────────┘
```

**虚拟节点优化：**
```
物理节点A → 虚拟节点A1, A2, A3（分散在环上）
→ 数据分布更均匀
```

**Kafka应用：**
```java
// 自定义分区器：一致性Hash
TreeMap<Long, Integer> ring = new TreeMap<>();
// 节点变化时，只影响相邻数据
```

---

### 4.3 对比表格（面试必答）

| 维度 | 哈希槽 | 一致性Hash |
|------|--------|-----------|
| **数据迁移量** | 迁移指定槽位 | 只迁移相邻节点 |
| **实现复杂度** | 简单 | 较复杂（需维护环） |
| **负载均衡** | 依赖槽位分配策略 | 虚拟节点优化后较好 |
| **典型应用** | Redis Cluster | 缓存、负载均衡 |
| **Kafka适用** | 固定分区数场景 | 分区数动态变化场景 |

## 六、常见追问及回答

### Q1: 增加Partition后，之前有序的消息会乱吗？
> **会。** 因为Key的Hash取模结果变了，同一Key可能进入不同Partition。
> 
> **解决：** 扩容前暂停写入，或用一致性Hash减少影响。

### Q2: 消费端多线程处理，怎么保证顺序？
> **方案：** 按Key哈希到不同线程，同一线程内顺序处理。
> ```java
> int threadIndex = Math.abs(key.hashCode()) % threadPoolSize;
> threadPool[threadIndex].submit(() -> process(msg));
> ```

### Q3: 生产者重试会导致乱序吗？
> **会。** 开启重试+`max.in.flight.requests.per.connection > 1`时，可能后发的消息先成功。
> 
> **解决：** 
> - 设置`max.in.flight.requests.per.connection = 1`（牺牲吞吐）
> - 或开启幂等性（`enable.idempotence=true`）

### Q4: 什么场景需要全局有序？
> 金融交易、状态机流转、日志采集（时间顺序）
> 
> **建议：** 能不用全局有序就不用，用业务Key局部有序替代。
