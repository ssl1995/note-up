# SpringCloud微服务面试题
## 微服务概念
### 什么是微服务？
**分析：**
微服务是一种架构思想，它将应用程序拆分为一系列小型、独立的服务，每个服务负责处理一项特定业务功能。
这种架构风格的特点是**服务之间松散耦合、独立部署和运行**。微服务架构使得开发人员可以更加专注于单个服务的开发与测试，降低了系统的复杂性，提高了系统的可维护性和可扩展性。同时，每个服务可以根据具体的业务需求选择合适的语言、工具进行构建，提高了系统的灵活性和可维护性。
在微服务架构中，**服务之间通过轻量级的通信机制（如RPC、HTTP等）进行通信**，每个服务都可以独立地进行部署、扩展和升级，从而提高了系统的可靠性和可用性。总的来说，微服务架构思想使得应用程序更加灵活、可维护和可扩展，为构建高效、可靠的大型应用程序提供了有力支持。
**回答：**
微服务就是把一个大的应用拆成多个小服务，每个服务负责一块具体的功能，比如用户管理、订单处理这些。每个小服务都是独立运行的，有自己的数据库，团队可以单独开发、测试、部署，不用等整个应用一起动。服务之间通过API互相调用，比如下单的时候，订单服务会调用用户服务查信息，调用支付服务处理钱。这样做的好处是，某个服务改功能或者出问题，基本不影响其他服务，开发速度快，出了问题也好定位是哪个服务的事。不过得注意服务之间的通信要稳定，不然调用太多容易乱。一般业务复杂、需要经常更新的项目适合用这种方式。
### 微服务相较于传统的web项目有什么优势？
**分析：**
传统的Web项目尽管也是遵循模块化开发，但最终它们会打包并部署为单体式应用。例如Java应用程序会被打包成WAR，部署在Tomcat或者Jetty上。
这种单体应用比较适合于小项目，优点是：
- 开发简单直接，集中式管理
- 基本不会重复开发
- 功能都在本地，没有分布式的管理开销和调用开销
它的缺点也十分明显，特别对于互联网公司来说：
- 开发效率低：所有的开发在一个项目改代码，递交代码相互等待，代码冲突不断
- 代码维护难：代码功能耦合在一起，新人不知道何从下手
- 部署不灵活：构建时间长，任何小修改必须重新构建整个项目，这个过程往往很长
- 稳定性不高：一个微不足道的小问题，可以导致整个应用挂掉
- 扩展性不够：无法满足高并发情况下的业务需求
主流的设计一般会采用微服务架构。其思路不是开发一个巨大的单体式应用，而是将应用分解为小的、互相连接的微服务。一个微服务完成某个特定功能，每个微服务都有自己的业务逻辑。一些微服务还会提供API接口给其他微服务和应用客户端使用
微服务架构的优点：
- 解决了复杂性问题：开发的速度要快很多，更容易理解和维护。
- 单独开发每个服务，与其他服务互不干扰
- 可以独立部署每个微服务
微服务的缺点：
- 多服务运维难度
- 系统部署依赖
- 服务间通信成本
- 数据一致性
- 系统集成测试
- 性能监控
**回答：**
微服务比传统web项目优势主要在这几方面。首先是独立部署，传统项目改一点功能可能要整个应用重新部署，微服务拆成小服务后，每个服务能单独开发、测试、上线，改一个服务不影响其他的，上线速度快多了。然后技术栈灵活，传统项目一般只能用一种语言框架，微服务不同服务能选适合的技术，比如用户服务用Java，推荐服务用Go，开发更灵活。还有可扩展性，传统项目要扩容就得整个应用加服务器，微服务哪个服务访问量大就单独给它加资源，不用浪费整个系统的资源。故障隔离也很重要，传统项目一个模块出问题可能整个应用崩掉，微服务一个服务挂了，其他服务还能正常跑，影响范围小。最后团队协作方便，小团队负责一个服务，沟通成本低，开发效率也高。
### 微服务带来了哪些挑战？
**分析：**
**成本挑战：**
- **基础设施成本增加：** 微服务应用通常需要更多的基础设施资源，例如服务器、容器管理、负载均衡器等，这可能导致运营成本增加。
- **开发和维护成本：** 管理多个微服务的开发、测试、部署和维护需要更多的工程师资源，这可能导致开发和维护成本上升。
**复杂性挑战：**
- **分布式系统复杂性：** 微服务应用是分布式系统，涉及多个独立运行的服务，这增加了系统的复杂性，包括网络通信、故障处理和事务管理等方面。
- **服务发现和治理：** 管理多个微服务的发现、注册、版本控制和路由需要额外的复杂性，例如使用服务网格或API网关。
**部署挑战：**
- **自动化部署需求：** 为了有效地部署多个微服务，需要建立自动化的部署流程，这可能需要额外的工作和资源。
- **版本控制和回滚：** 管理不同版本的微服务以及版本之间的兼容性可能会变得复杂，特别是在需要回滚时。
**一致性挑战：**
- **数据一致性：** 不同微服务可能拥有各自的数据存储，确保数据一致性和同步可能需要复杂的解决方案，如分布式事务或事件驱动的一致性。
- **事务管理：** 管理跨多个微服务的事务变得复杂，确保事务的一致性和隔离性需要额外的努力和技术。
**监控和故障排除挑战：**
- **性能监控：** 在微服务环境中，跟踪性能问题和故障排除可能更加困难，因为问题可能涉及多个服务，需要强大的监控和诊断工具。
- **故障排除：** 需要有效的方法来跟踪和诊断跨多个服务的故障，以便快速恢复。
微服务不是万金油，是用来处理海量用户、业务复杂和需求频繁变更场景下的一种架构风格。引用一句话“好的架构是演化出来的，而不是设计出来的”。任何一种架构的引入，都会带来利弊两个方面的影响，如何平衡才最重要。
**回答：**
微服务虽然能让系统更灵活，但挑战也不少。首先是分布式系统本身的复杂度，服务数量多了，调用链路就长，出问题的时候不好定位具体是哪个环节出了问题。然后是服务间通信，以前单体应用直接调用方法就行，现在得通过网络，网络不稳定就可能出现调用失败、超时这些情况，得处理重试、熔断这些问题。数据方面也麻烦，每个服务基本都有自己的数据库，跨服务的事务就很难保证一致性，不像单体应用那样一个本地事务就能搞定。部署和运维成本也会增加，服务多了，环境配置、版本控制都要单独管，还得用容器编排工具来管理，人力投入会变多。监控也得跟上，单个服务出问题可能会影响好几个依赖它的服务，得做全链路追踪和日志汇总，才能快速找到问题在哪。另外服务之间的依赖关系也复杂，一个服务升级了，可能会影响依赖它的其他服务，兼容性问题得提前考虑。
### 实现微服务要解决的四个问题？
**分析：**
**客户端如何访问这些服务？**
原来的服务都是可以进行单独调用，现在按功能拆分成独立的服务，变成了一个独立的Java进程了。客户端如何访问后台N个服务呢？
一般在后台N个服务和UI之间会一个代理或者叫API Gateway，它的作用包括：
- 提供统一服务入口，让微服务对前台透明
- 聚合后台的服务，节省流量，提升性能
- 提供安全，过滤，流控等API管理功能
**服务之间如何通信？**
因为所有微服务都是独立的Java进程跑在独立的虚拟机上，所以服务间的通信就是IPC（inter process communication，进程间通信），已经有很多成熟的方案。现在基本最通用的有两种方式：
- 同步调用
  - REST
  - RPC
- 异步消息调用（Kafka, ActiveMQ、RocketMQ）
**这么多服务，怎么找？**
在微服务架构中，一般每一个服务都是有多个拷贝，来做负载均衡。一个服务随时可能下线，也可能应对临时访问压力增加新的服务节点。服务之间如何相互感知？服务如何管理？这就是服务发现的问题了。
一般都是通过zookeeper等类似技术做服务注册信息的分布式管理。当服务上线时，服务提供者将自己的服务信息注册到ZK（或类似框架），并通过心跳维持长链接，实时更新链接信息。服务调用者通过ZK寻址，根据可定制算法，找到一个服务，还可以将服务信息缓存在本地以提高性能。当服务下线时，ZK会发通知给服务客户端。
- 客户端做：优点是架构简单，扩展灵活，只对服务注册器依赖。缺点是客户端要维护所有调用服务的地址，有技术难度，一般大公司都有成熟的内部框架支持，比如Dubbo。
- 服务端做：优点是简单，所有服务对于前台调用方透明，一般在小公司在云服务上部署的应用采用的比较多。
**服务挂了怎么办？**
分布式最大的特性就是网络是不可靠的。通过微服务拆分能降低这个风险，不过如果没有特别的保障，结局肯定是噩梦。
当我们的系统是由一系列的服务调用链组成的时候，我们必须确保任一环节出问题都不至于影响整体链路。相应的手段有很多：
- 重试机制
- 限流
- 熔断机制
- 负载均衡
- 降级（本地缓存）
**回答：**
实现微服务主要得解决四个问题。首先是服务通信，微服务是独立部署的，服务之间得互相调用，得确定用什么方式通信，比如HTTP还是RPC，接口怎么定义，确保调用能正常进行。然后是服务发现，服务实例可能随时扩缩容或重启，地址会变，得有机制让调用方找到对应的服务，通常需要注册中心来管理服务地址。第三个是数据一致性，每个微服务一般有自己的数据库，跨服务操作时，不能像单体应用那样用本地事务，得想办法保证数据一致，比如用最终一致性的方案。最后是服务治理，服务多了之后，某个服务出问题可能影响其他服务，得做熔断、限流避免级联故障，还要有监控，及时发现和处理问题。
### 微服务的通讯方式有哪些？
**分析：**
微服务的通讯方式主要有以下几种：
1. **RESTful API**：基于 HTTP 协议的 RESTful API 是最常用的微服务通讯方式之一。服务之间通过 HTTP 请求和响应进行通讯，实现数据交换。这种方式简单、通用，适用于各种场景，但可能不适合对实时性要求非常高的场景。
2. **RPC（远程过程调用）**：RPC 允许一个服务像调用本地方法一样调用另一个服务的方法。它通过将方法调用封装成网络数据包并在不同的进程之间传输，实现不同服务之间的互相调用。RPC 方式可以提高调用的效率和性能，但可能需要更多的配置和管理工作。
3. **消息队列通讯**：如 RabbitMQ、Kafka、RocketMQ 等，服务之间不直接调用，而是通过消息队列进行异步消息传递，实现服务之间的解耦和异步处理。
4. **事件驱动通讯**：服务之间通过事件触发通讯，一旦某个服务发生了某个事件，就会触发其他服务的响应。这种方式可以实现服务的松耦合和事件的实时处理，典型的实现如 Event Bus。
5. **WebSocket（长连接通信）**：使用 WebSocket 实现双向通信，常用于实时推送场景，服务间可以维持长期的 TCP 连接进行数据交换。

  - **gRPC**：Google 开发的高性能、通用的开源 RPC 框架，它主要面向移动应用开发并基于 HTTP/2 协议标准设计。gRPC 使用 ProtoBuf（Protocol Buffers）作为序列化工具和接口定义语言，要求在调用前需要先定义好接口契约，并使用工具生成代码，然后在代码中调用这些生成的类进行服务调用。
### 分布式和微服务有什么区别？
**分析：**
它们的本质的区别体现在“目标”上。
- 分布式架构的目标就是访问量很大一台机器承受不了，或者是成本问题，不得不使用多台机器来完成服务的部署；
- 微服务的目标只是让各个模块拆分开来，不会被互相影响，比如模块的升级或者出现BUG或者是重构等等都不要影响到其他模块，微服务它是可以在一台机器上部署；
分布式也是微服务的一种，微服务也属于分布式。
**回答：**
分布式和微服务主要从不同角度说的。分布式更多是部署层面，把系统拆到多个节点或服务器上跑，多个部分协同工作，主要解决单点性能不够、资源利用的问题，比如一个应用拆成几块分别放不同机器。微服务是架构设计层面，按业务功能拆成独立的小服务，每个服务能单独开发、测试、部署，服务间通过接口通信，主要解决业务耦合紧、迭代慢的问题，比如电商里订单、支付各是一个服务。微服务通常会用分布式部署，但分布式不一定是微服务，比如一个应用拆成多节点跑还是一个整体，就只是分布式不是微服务。
### **单体应用、SOA 和微服务架构有什么区别？**
**分析：**
单体应用、SOA和微服务架构都是不同的架构风格，适用于不同的情况。
- **单体应用像一个整体，所有的功能都打包在一个应用中**。这种架构风格容易部署和测试，但随着系统规模的扩大，它的灵活性和可维护性会降低。
- **SOA是一种面向服务的架构风格，将系统划分为多个独立的服务**。这些服务可以通过网络调用，并且可以跨平台、跨语言进行交互。SOA的优点是提供了跨系统的服务复用和松散耦合的交互方式，但实现SOA需要投入大量的工作，包括服务的定义、接口的选择、协议的制定等。
- **微服务架构进一步将系统划分为多个小型、独立的服务**，每个服务都是一个单独的应用程序，可以独立部署、运行和扩展。微服务架构具有更高的灵活性和可维护性，适用于复杂的大型系统，强调服务的自治和独立性。但是，实施微服务架构也需要投入大量的工作，包括服务的定义、通信机制的选择、服务的管理等。
**回答：**
单体应用就是把所有功能都放一个应用里，代码、数据库都在一起，部署就一个包，小项目开发快，但功能多了后改一点代码可能影响整个系统，扩展也麻烦。SOA是按业务拆成几个服务，像订单服务、用户服务这样，服务间通过总线通信，服务比单体大但比微服务粗，可能还共享数据库，耦合没完全解决。微服务拆得更细，每个服务独立部署，有自己的数据库，服务间直接用API调用，单个服务改起来方便，扩展灵活，但服务多了管理起来复杂。主要区别就在拆分粒度和独立性上，单体最集中，SOA中等拆分，微服务最细且独立。
### 现在有哪些流行的微服务解决方案？
**分析：**
目前最主流的微服务开源解决方案有三种：
Dubbo：
- Dubbo 是一个高性能、轻量级的 Java 微服务框架，最初由阿里巴巴（Alibaba）开发并于2011年开源。它提供了服务注册与发现、负载均衡、容错、分布式调用等功能，后来一度停止维护，在近两年，又重新开始迭代，并推出了Dubbo3。
- Dubbo 使用基于 RPC（Remote Procedure Call）的通信模型，具有较高的性能和可扩展性。它支持多种传输协议（如TCP、HTTP、Redis）和序列化方式（如JSON、Hessian、Protobuf），可根据需求进行配置。
- Dubbo更多地被认为是一个高性能的RPC（远程过程调用）框架，一些服务治理功能依赖于第三方组件实现，比如使用ZooKeeper、Apollo等等。
Spring Cloud Netflix：
- Spring Cloud Netflix 是 Spring Cloud 的一个子项目，结合了 Netflix 开源的多个组件，但是Netflix自2018年停止维护和更新Netflix OSS项目，包括Eureka、Hystrix等组件，所以Spring Cloud Netflix也逐渐进入了维护模式。
- 该项目包含了许多流行的 Netflix 组件，如Eureka（服务注册与发现）、Ribbon（客户端负载均衡）、Hystrix（断路器）、Zuul（API 网关）等。它们都是高度可扩展的、经过大规模实践验证的微服务组件。
Spring Cloud Alibaba：
- Spring Cloud Alibaba 是 Spring Cloud 的另一个子项目，与阿里巴巴的分布式应用开发框架相关。它提供了一整套与 Alibaba 生态系统集成的解决方案。

7. 限流和降级：用于防止微服务过载，对请求进行限制和降级处理。常见的实现包括：
   - Spring Cloud Netflix：Hystrix
   - Spring Cloud Alibaba：Sentinel
8. 分布式追踪和监控：用于跟踪和监控微服务的请求流程和性能指标。常见的实现包括：

### 微服务架构如何运行的？
**分析：**

- **客户端**  – 来自不同设备的不同用户发送请求。
- **身份提供商**  – 验证用户或客户身份并颁发安全令牌。
- **API网关**  – 处理客户端请求。
- **静态内容**  – 容纳系统的所有内容。
- **管理**  – 在节点上平衡服务并识别故障。
- **服务发现**  – 查找微服务之间通信路径的指南。
- **内容交付网络**  – 代理服务器及其数据中心的分布式网络。
- **远程服务**  – 启用驻留在IT设备网络上的远程访问信息。
**回答：**
微服务架构运行起来，核心是把一个大系统拆成多个独立的小服务，每个服务负责一块具体功能，像用户服务管登录注册、订单服务管下单流程。这些小服务各自独立开发、部署，用自己的数据库，互不干扰。服务之间要通信，一般通过HTTP接口或者RPC调用。服务多了不好找，所以会有注册中心，服务启动时把自己的地址注册进去，调用方需要时就从注册中心查地址。用户请求进来先经过API网关，网关再转发到对应的服务。要是某个服务出问题，会有熔断、降级这些机制，防止故障扩散影响整个系统。这样每个服务能单独扩缩容，出问题也好定位，整体系统更灵活。

**回答：**

## 服务注册与发现
### 为什么需要服务注册发现？
**分析：**
在分布式系统中，服务的数量和规模通常很大，同时服务的部署和变化也非常频繁。因此，手动管理和调用这些服务会变得非常困难和繁琐。服务注册与发现的作用就是解决这个问题，它提供了一种机制，让服务可以自动注册到注册中心，并且可以通过注册中心进行查询和调用。
服务注册与发现的核心思想是通过注册中心来维护服务提供者和服务消费者之间的映射关系。当服务提供者启动时，它会向注册中心注册自己的信息，包括服务名、IP 地址、端口号等信息。当服务消费者需要调用某服务时，它可以向注册中心发起查询请求，查询对应服务的地址信息，然后通过该地址发送请求。
使用服务注册与发现的好处是:
- 自动化管理：服务的自动注册和发现可以减少手动管理服务的工作量，提高系统的可靠性和稳定性，同时也可以减少出错的机会。
- 负载均衡：注册中心可以提供负载均衡的功能，当有多个服务提供者时，它可以自动帮助消费者进行负载均衡。
- 服务治理：通过服务注册中心，可以方便地进行服务的监控、管理和治理，例如限流、降级、熔断等操作。
- 服务拓扑发现：服务注册中心可以提供服务拓扑发现的功能，帮助开发者更好地理解和管理服务之间的关系。
**回答：**
在分布式系统里，服务数量通常很多，每个服务可能有多个运行实例，而且这些实例的地址、端口经常会变，比如服务扩容、缩容或者故障重启的时候。要是没有服务注册发现，客户端调用服务就得手动写死地址，服务一变调用就失败，手动改地址又麻烦还容易出错。服务注册发现就是让服务启动时把自己的地址、状态信息注册到注册中心，客户端需要调用服务时，直接去注册中心查询最新的可用服务地址。这样不管服务实例怎么动态变化，客户端都能拿到可用地址，不用操心具体位置。而且注册中心能实时监控服务实例是否健康，把故障实例剔除掉，客户端就只会调用正常的实例，还能根据实例状态实现负载均衡，避免某个实例压力太大。所以服务注册发现主要就是解决服务地址动态管理的问题，让系统不用手动维护服务位置，调用更灵活，也更稳定。
### SpringCloud可以选择哪些注册中心？
**分析：**
SpringCloud可以与多种注册中心进行集成，常见的注册中心包括：
1. Eureka：Eureka 是 Netflix 开源的服务发现框架，具有高可用、弹性、可扩展等特点，并与 Spring Cloud 集成良好，**已闭源**。AP（可用性和分区容忍性）
2. Consul：Consul 是一种分布式服务发现和配置管理系统，由 HashiCorp 开发。它提供了服务注册、服务发现、健康检查、键值存储等功能，并支持多数据中心部署。CP（一致性和分区容忍性）
3. ZooKeeper：ZooKeeper 是 Apache 基金会开源的分布式协调服务，可以用作服务注册中心。它具有高可用、一致性、可靠性等特点。 CP（一致性和分区容忍性）
4. Nacos：Nacos 是阿里巴巴开源的一个动态服务发现、配置管理和服务管理平台。它提供了服务注册和发现、配置管理、动态 DNS 服务等功能。 既支持AP，也支持CP
5. etcd：etcd 是 CoreOS 开源的一种分布式键值存储系统，可以被用作服务注册中心。它具有高可用、强一致性、分布式复制等特性。 CP（一致性和分区容忍性）
**回答：**
SpringCloud常用的注册中心主要有Eureka、Consul、Nacos这几个。Eureka是Netflix开源的，轻量级，遵循AP原则，更注重可用性，服务挂了不会影响整体，适合分布式系统，但一致性稍弱。Consul是HashiCorp的，支持服务发现和配置管理，遵循CP原则，强一致性，适合需要严格一致性的场景，不过可用性会差一点。Nacos是阿里开源的，功能比较全，既能当注册中心也能做配置中心，还支持AP和CP模式切换，部署简单，现在项目里用得比较多，因为能一站式解决问题。另外Zookeeper虽然传统，但SpringCloud里用得少了，主要是CP原则，适合强一致场景但不够灵活。实际选的时候看项目需求，现在Nacos更主流一些。
### 什么是**Eureka？**
**分析：**
Eureka是Netflflix开发的服务注册发现框架，SpringCloud将它集成在⾃⼰的⼦项⽬spring-cloud-netflflix中，实现SpringCloud的服务注册发现功能。 
Eureka Client是⼀个Java客户端，⽤于简化与Eureka Server的交互。 Eureka Server提供服务发现的能⼒，各个微服务启动时，会通过Eureka Client向Eureka Server进⾏注册⾃⼰的信息（例如⽹络信息），Eureka Server会存储该服务的信息。 
微服务启动后，会周期性地向Eureka Server发送⼼跳（默认周期为30秒）以续约⾃⼰的信息。如果 Eureka Server在⼀定时间内没有接收到某个微服务节点的⼼跳，Eureka Server将会注销该微服务节点 
（默认90秒）
**回答：**
Eureka是微服务架构里常用的服务注册发现工具，主要帮服务之间互相找到并通信。简单说，它有个服务器端叫Eureka Server，各个服务启动时会把自己的信息比如地址、端口注册到这个服务器上。注册后，服务会定期给服务器发心跳，告诉服务器自己还在运行，要是长时间没发心跳，服务器就会把这个服务从注册列表里删掉。其他服务需要调用的时候，就去Eureka Server拿最新的服务列表，知道要调用的服务在哪儿，然后直接发起请求。为了保证稳定，Eureka Server通常会部署集群，多台服务器互相备份，就算有一台出问题，其他服务器还能继续工作，避免单点故障影响整个系统。
### **Eureka**实现原理说一下
**分析：**
Eureka的实现原理，大概可以从这几个方面来看：
1. 服务注册与发现: 当一个服务实例启动时，它会向Eureka Server发送注册请求，将自己的信息注册到注册中心。Eureka Server会将这些信息保存在内存中，并提供REST接口供其他服务查询。服务消费者可以通过查询服务实例列表来获取可用的服务提供者实例，从而实现服务的发现。
2. 服务健康检查: Eureka通过心跳机制来检测服务实例的健康状态。服务实例会定期向Eureka Server发送心跳，也就是续约，以表明自己的存活状态。如果Eureka Server在一定时间内没有收到某个服务实例的心跳，则会将其标记为不可用，并从服务列表中移除，下线实例。
3. 服务负载均衡: Eureka客户端在调用其他服务时，会从本地缓存中获取服务的注册信息。如果缓存中没有对应的信息，则会向Eureka Server发送查询请求。Eureka Server会返回一个可用的服务实例列表给客户端，客户端可以使用负载均衡算法选择其中一个进行调用。
其它的注册中心，如Nacos、Consul等等，在服务注册和发现上，实现原理都是大同小异。
**回答：**
Eureka是Netflix的服务发现组件，主要用来实现服务注册和发现。服务启动的时候会主动把自己的IP、端口、服务名这些信息注册到Eureka Server，Server收到后就把这些信息存到本地的注册表。注册完成后服务会定期发心跳给Server，默认30秒一次，告诉Server自己还正常运行。要是Server超过90秒没收到某个服务的心跳，就会把这个服务从注册表删掉。其他服务需要调用的时候，会先从Server拉取注册表缓存到本地，调用时就从本地缓存里找可用的服务，再通过负载均衡选一个具体的服务实例发请求。另外Eureka还有自我保护机制，当短时间内大量服务的心跳失败，Server会判断可能是网络问题，这时候不会马上删除这些服务，避免误删健康的服务，保证整体的可用性。
### **Eureka怎么实现高可用？**
**分析：**
- 多实例部署: 通过将多个Eureka Server实例部署在不同的节点上，可以实现高可用性。当其中一个实例发生故障时，其他实例仍然可以提供服务，并保持注册信息的一致性。
- 服务注册信息的复制: 当一个服务实例向Eureka Server注册时，每个Eureka Server实例都会复制其他实例的注册信息，以保持数据的一致性。当某个Eureka Server实例发生故障时，其他实例可以接管其工作，保证整个系统的正常运行。
- 自我保护机制: Eureka还具有自我保护机制。当Eureka Server节点在一定时间内没有接收到心跳时，它会进入自我保护模式。在自我保护模式下，Eureka Server不再剔除注册表中的服务实例，以保护现有的注册信息。这样可以防止由于网络抖动或其他原因导致的误剔除，进一步提高系统的稳定性。
**回答：**
Eureka实现高可用主要靠集群部署和一些配置。首先得部署多个Eureka Server实例，这些实例之间要互相注册，形成一个集群。这样每个Server都能接收服务注册、处理心跳请求，并且会同步彼此的服务注册表数据，就算某个Server挂了，其他的还能正常工作。然后客户端注册服务的时候，配置文件里要写多个Eureka Server的地址，别只配一个，这样就算有Server不可用，客户端还能连其他的，不会因为单个Server故障就注册不上。另外Eureka有个自我保护机制也很重要，当网络出现抖动，Server收不到某个服务的心跳时，不会马上把这个服务从注册表删掉，而是保留它，避免因为临时网络问题误删服务实例，保证整体的可用性。大概就是这些关键点，通过集群互备、客户端多地址配置和自我保护，来实现高可用。
### **Eureka自我保护模式是什么？**
**分析：**
默认情况下，如果Eureka Server在⼀定时间内没有接收到某个微服务实例的⼼跳，Eureka Server将会注销该实例（默认90秒）。但是当⽹络分区故障发⽣时，微服务与Eureka Server之间⽆法正常通信， 以上⾏为可能变得⾮常危险了——因为微服务本身其实是健康的，此时本不应该注销这个微服务。 
Eureka通过“⾃我保护模式”来解决这个问题——当Eureka Server节点在短时间内丢失过多客户端时 （可能发⽣了⽹络分区故障），那么这个节点就会进⼊⾃我保护模式。⼀旦进⼊该模式，Eureka Server就会保护服务注册表中的信息，不再删除服务注册表中的数据（也就是不会注销任何微服务）。 当⽹络故障恢复后，该Eureka Server节点会⾃动退出⾃我保护模式。 
综上，⾃我保护模式是⼀种应对⽹络异常的安全保护措施。它的架构哲学是宁可同时保留所有微服务 （健康的微服务和不健康的微服务都会保留），也不盲⽬注销任何健康的微服务。使⽤⾃我保护模式，可以让Eureka集群更加的健壮、稳定。 
**回答：**
Eureka自我保护模式其实就是Eureka Server的一种保护机制。当Server在一定时间内，默认是90秒，收到的服务心跳失败比例超过15%的时候，就会进入这个模式。主要是为了防止网络出问题的时候，比如网络分区，服务其实是正常的，但心跳没传到Server，这时候Server如果把这些服务删掉就不对了。所以进入自我保护模式后，Server就不会再剔除任何服务实例，不管这些实例是不是真的挂了。同时它会提示保护模式开启，直到网络恢复，心跳正常了，失败比例低于15%，才会退出这个模式。这样就能避免因为网络波动误删健康服务，保障整个微服务架构的高可用。

### **Eureka和**ZooKeeper的区别是什么？
**分析：**
**Zookeeper保证了CP，Eureka保证了AP。【A：高可用 C：一致性 P：分区容错性】**
**Eureka满⾜可⽤性，Zookeeper满⾜⼀致性：** 
- Zookeeper要求各个服务之间同步完成之后才会返回给⽤户结果，如果服务出现⽹络波动导致监听不到⼼跳，会⽴即从服务列表中剔除，服务不可⽤。 
- Eureka如果遇到⽹络故障，基于Eureka的⾃我保护机制，不会⽴即剔除服务，虽然⽤户获取的服务不⼀定是可⽤的，但是⾄少可以获取到服务列表。⽤户访问服务列表后还可以利⽤重试机制，找到正确的服务。更符合分布式服务⾼可⽤的要求。 
**Eureka集群节点间相互平等，Zookeeper有主从之分：** 
- 如果Zookeeper集群中有服务宕机，会重新基于选举机制选出新的主节点，因此可能会导致整个集群因为选主⽽阻塞，服务不可⽤。 
- Eureka集群有服务宕机，因为各个节点之间是平等的，其他服务器不受影响。
**Eureka中服务发现者是去主动地拉取服务，Zookeeper服务发现者是基于监听机制：** 
- Eureka中获取服务列表后会缓存起来，每隔30秒重新拉取服务列表。 
-  Zookeeper是监听节点的信息变化，当服务节点信息发⽣变化的时候，客户端⽴即收到通知。 
**回答：**
Eureka和ZooKeeper都是服务注册中心，但设计思路和适用场景不一样。Eureka遵循AP原则，就是可用性和分区容错性优先，它的节点都是平等的，没有主从之分，某个节点挂了其他节点还能正常工作，整体可用性高。服务注册后会定期发心跳续约，要是超时没收到心跳，Eureka不会马上删服务，有自我保护机制，网络抖动时能避免误删，适合对可用性要求高的分布式系统。
ZooKeeper遵循CP原则，也就是一致性和分区容错性优先，它是主从架构，有一个主节点和多个从节点，主节点挂了会触发选举，选举期间整个系统不可用，这时候服务注册发现会受影响，但数据一致性强。它用ZAB协议保证数据同步，适合需要强一致性的场景，比如分布式锁。
简单说，Eureka更看重可用性，适合微服务这种需要持续提供服务的场景；ZooKeeper更看重一致性，但会牺牲部分可用性，适合能接受短暂不可用但要求数据一致的场景。

### **Nacos的服务注册表结构是怎样的？**
**分析：**
Nacos采用了数据的分级存储模型，最外层是Namespace，用来隔离环境。然后是Group，用来对服务分组。接下来就是服务（Service）了，一个服务包含多个实例，但是可能处于不同机房，因此Service下有多个集群（Cluster），Cluster下是不同的实例（Instance）。
对应到Java代码中，Nacos采用了一个多层的Map来表示。结构为Map<String, Map<String, Service>>，其中最外层Map的key就是namespaceId，值是一个Map。内层Map的key是group拼接serviceName，值是Service对象。Service对象内部又是一个Map，key是集群名称，值是Cluster对象。而Cluster对象内部维护了Instance的集合。
**回答：**
Nacos的服务注册表主要存服务和实例的信息。最上层是命名空间，用来隔离不同环境的服务，比如开发和生产环境。每个命名空间下有多个服务，服务用服务名作为唯一标识，还包含一些元数据，像创建时间、健康检查的配置。每个服务下面有多个实例，实例是具体提供服务的节点，包含IP、端口这些基础信息，还有健康状态，比如是不是健康的，能不能接收请求。实例也有元数据，比如权重，用来做负载均衡时分配请求，还有集群信息，区分不同机房或区域的实例。整体是按命名空间、服务、实例这样的层级来组织的，方便快速查找和管理服务实例。
### **Nacos中的Namespace是什么？如何使用它来组织和管理微服务？**
**分析：**
**Nacos中的Namespace是用于隔离不同环境或应用之间的配置和服务信息的概念。**通过使用Namespace，可以将不同的环境（例如开发、测试和生产）或不同的应用程序（例如Web应用和移动应用）的配置和服务信息分离开来，以避免冲突和错误。
在Nacos中，每个Namespace都有自己独立的配置和服务注册表。这意味着，如果您有多个应用程序需要使用Nacos，您可以将它们分别放置在不同的Namespace中。每个Namespace都有自己的命名空间ID，用于标识该Namespace。要使用Namespace，在Nacos客户端初始化时，您需要指定要使用的Namespace ID。
通过使用Namespace，您可以对不同Namespace下的服务进行分组和管理，例如可以使用Nacos提供的Group功能对同一Namespace下的服务进行分组，方便管理和查找。同时，使用Namespace还可以对不同环境下的配置进行隔离，避免不同环境之间的配置冲突。
**回答：**
Nacos里的Namespace简单说就是用来隔离资源的，像配置文件、服务注册这些都能隔离开。平时管理微服务的时候，最常用的就是按环境分，比如开发、测试、生产各建一个Namespace，这样不同环境的服务和配置就不会混在一起，避免互相影响。另外也能按业务线分，比如订单业务、用户业务各用自己的Namespace，方便不同团队管理。用的时候先在Nacos控制台创建Namespace，会生成一个ID，然后微服务在配置文件里指定这个Namespace ID，启动的时候就会注册到对应的Namespace里，配置也只会加载自己Namespace下的，这样资源隔离就做好了，管理起来也清晰。
## 负载均衡
### 为什么需要负载均衡？
**分析：**
在分布式系统中，服务通常会部署在多个节点上，每个节点的负载不一定相同，当服务请求量较大时，可能会导致某些节点的负载过高，从而影响服务的性能和响应速度。负载均衡的作用就是解决这个问题。
负载均衡是一种将请求分发到多个节点上的技术，它可以使每个节点的负载均衡，从而提高整个系统的性能和响应速度。
**回答：**
负载均衡主要是解决服务器处理请求时的压力问题。当用户访问量增加的时候，单台服务器处理不过来，容易变慢甚至崩溃，这时候就得用多台服务器一起分担压力。负载均衡就是把用户的请求合理分配到这些服务器上，不让某一台服务器太忙，其他的又闲着，这样能让资源利用更均匀，也避免了单点故障。要是某台服务器出问题了，负载均衡能自动把请求转到正常的服务器上，用户基本感觉不到影响。同时，请求分散后，服务器处理起来更快，用户等的时间短，体验也会更好。所以总的来说，负载均衡主要是为了提高系统的稳定性、资源利用率和用户体验。
### 负载均衡的实现方式有哪些？
**分析：**
负载均衡可以有多种实现方式，其中常见的有如下几种:
- 客户端负载均衡：在客户端实现负载均衡，当客户端需要调用服务时，它会从多个服务提供者中选择一个最优的节点进行调用。这种方式通常需要使用负载均衡算法，例如轮询、随机、一致性哈希等。
- 服务端负载均衡:在服务端实现负载均衡，当客户端请求到达服务端时，服务端会根据一定的规则选择一个最优的节点进行处理。这种方式通常需要使用负载均衡器，例如 Nginx、HAProxy 等。
**回答：**
负载均衡实现方式主要有这么几种。首先是硬件负载均衡，用专门的硬件设备，像F5这种，性能很强，能扛住高并发，但成本也高，一般大企业用得多。然后是软件负载均衡，靠软件实现，比如Nginx、LVS这些，成本低，配置灵活，中小公司常用，现在云环境里也用得多。还有DNS负载均衡，就是通过DNS服务器解析域名时返回不同的服务器IP，把请求分到不同机器上，简单好实现，但控制精度低，调整起来慢。另外还有基于网络层的，比如修改IP地址转发请求，或者链路层的，直接改MAC地址转发，这种效率更高，像LVS的一些模式就是这么做的。总的来说，硬件强但贵，软件灵活成本低，DNS简单但不精确，网络层和链路层的效率比较高，具体用哪种看实际需求。
### 在Spring Cloud中，怎么实现服务的负载均衡？
**分析：**
在Spring Cloud中，可以使用Ribbon实现服务的负载均衡。Ribbon是一个客户端负载均衡器，它可以根据配置的负载均衡策略选择合适的服务实例进行调用。
**回答：**
在Spring Cloud里实现服务负载均衡，首先服务得注册到注册中心，像Eureka或者Nacos都行，这样消费者才能知道有哪些服务实例。然后客户端调用时用Spring Cloud LoadBalancer，先引入对应的依赖，比如spring-cloud-starter-loadbalancer。接着配置RestTemplate的时候加上@LoadBalanced注解，这样调用服务时就会自动做负载均衡了。它默认策略一般是轮询，就是按顺序挨个调用服务实例，也能自定义策略，比如随机选或者根据服务健康状态来选。这样请求就能分摊到不同实例上，避免单个服务压力太大，实现负载均衡。
### 负载均衡有什么策略？
**分析：**
1. **轮询算法（Round Robin）**：轮询算法是最简单的负载均衡算法之一。它按照顺序将请求依次分配给每个后端服务器，循环往复。当请求到达时，负载均衡器按照事先定义的顺序选择下一个服务器。轮询算法适用于后端服务器具有相同的处理能力和性能的场景。
2. **加权轮询算法（Weighted Round Robin）**：加权轮询算法在轮询算法的基础上增加了权重的概念。每个后端服务器都被赋予一个权重值，权重值越高，被选中的概率就越大。这样可以根据服务器的处理能力和性能调整请求的分配比例，使得性能较高的服务器能够处理更多的请求。
3. **随机算法（Random）**：随机算法将请求随机分配给后端服务器。每个后端服务器有相等的被选中概率，没有考虑服务器的实际负载情况。这种算法简单快速，适用于后端服务器性能相近且无需考虑请求处理能力的场景。
4. **加权随机算法（Weighted Random）**：加权随机算法在随机算法的基础上引入了权重的概念。每个后端服务器被赋予一个权重值，权重值越高，被选中的概率就越大。这样可以根据服务器的处理能力和性能调整请求的分配比例。
5. **最少连接算法（Least Connection）**：最少连接算法会根据后端服务器当前的连接数来决定请求的分配。负载均衡器会选择当前连接数最少的服务器进行请求分配，以保证后端服务器的负载均衡。这种算法适用于后端服务器的处理能力不同或者请求的处理时间不同的场景。
6. **哈希算法（Hash）**：哈希算法会根据请求的某个特定属性（如客户端IP地址、请求URL等）计算哈希值，然后根据哈希值选择相应的后端服务器。
常见的负载均衡器，比如Ribbion、Gateway等等，基本都支持这些负载均衡算法。
**回答：**
负载均衡常用的策略有这么几种。轮询就是按顺序把请求分给服务器，一个接一个，实现简单，但如果服务器性能不一样，负载可能不均匀。加权轮询会给性能好的服务器设高点权重，让它多处理请求，能解决服务器性能差异的问题。IP哈希是根据客户端IP计算分配，同一个用户会固定到一台服务器，适合需要会话保持的场景。最少连接策略会看服务器当前连接数，新请求分给连接少的，能动态调整负载。加权最少连接就是结合权重和连接数，更灵活适应不同服务器性能。这些是比较基础常用的，实际用的时候根据服务器性能、是否需要会话保持这些场景来选就行。
### 什么是**Ribbon？**
**分析：**
Ribbon是Spring Cloud Netflix组件中⼀个基于HTTP和TCP的客户端负载均衡⼯具，它基于Netflix Ribbon实现。当多个服务提供者时，Ribbon可以根据负载均衡的算法，⽐如：简单轮询、随机连接等，⾃动地选择需要调⽤的服务地址。 
**回答：**
Ribbon是Netflix开发的客户端负载均衡工具，主要用在微服务架构里。当客户端需要调用其他服务时，它能从服务注册中心拿到可用的服务实例列表，再根据设定的策略选择一个实例来发请求，这样能让请求分配更均匀，避免某个服务实例压力太大。常见的策略有轮询、随机、根据响应时间加权这些，默认是轮询。它跟Nginx那种服务端负载均衡不一样，是在客户端这边做的，不需要额外部署中间件，直接集成在客户端里用。比如Spring Cloud里就经常把它和Eureka配合，客户端通过Ribbon自动获取服务列表并做负载均衡，不用手动写代码选实例，挺方便的。
### **Ribbon和 nginx 的区别是什么？**
**分析：**
- Nginx是服务器负载均衡，客户端所有请求都会交给nginx，然后由nginx实现转发请求。即负载均衡是由服务端实现的。
- Ribbon本地负载均衡，在调用微服务接口时候，会在注册中心上获取注册信息服务列表之后缓存到JVM本地，从而在本地实现RPC远程服务调用技术。
**回答：**
Ribbon和Nginx都是做负载均衡的，但工作位置不一样。Ribbon是客户端负载均衡器，它集成在服务消费者的应用里，比如微服务中A服务调用B服务时，Ribbon就在A服务这边根据策略（像轮询、随机）选择B服务的具体实例。Nginx是服务端负载均衡器，它是独立部署的中间件，客户端请求先到Nginx，再由Nginx转发到后端服务器集群。实现方式上，Ribbon是代码层面的，项目里引入依赖后通过配置使用；Nginx是改配置文件定义转发规则。适用场景不同，Ribbon主要用于微服务架构里服务间调用的负载均衡，Nginx多作为流量入口处理客户端直接发来的请求，比如网站请求转发到后端服务器。
## 远程调用
### 能说下HTTP和RPC的区别吗？
**分析：**
严格来讲，HTTP和不是一个层面的东西：
- HTTP（Hypertext Transfer Protocol）是一种应用层协议，主要强调的是网络通信；
- RPC（Remote Procedure Call，远程过程调用）是一种用于分布式系统之间通信的协议，强调的是服务之间的远程调用。
一些RPC框架比如gRPC，底层传输协议其实也是用的HTTP2，包括Dubbo3，也兼容了gRPC，使用了HTTP2作为传输层的一层协议。
| **区别** | **HTTP** | **RPC** |
|-|-|-|
| 定义 | HTTP(超文本传输协议)是一  <br/>种用于传输超文本的协议。 | RPC(远程过程调用)是一种用  <br/>于实现分布式系统中不同节点  <br/>之间通信的协议。 |
| 通信方式 | 基于请求-响应模型,客户端发  <br/>送请求,服务器返回响应。 | 基于方法调用模型,客户端调  <br/>用远程方法并等待结果。 |
| 传输协议 | 基于TCP协议,可使用其他传输  <br/>层协议如TLS/SSL进行安全加  <br/>密。 | 可以使用多种传输协议,如  <br/>TCP、UDP等。 |
| 数据格式 | 基于文本,常用的数据格式有  <br/>JSON、XML等。 | 可以使用各种数据格式,如二  <br/>进制、JSON、Protocol Buffers  <br/>等。 |
| 接口定义 | 使用RESTful风格的接口进行定  <br/>义,常用的方法有GET、  <br/>POST、PUT、DELETE等。 | 使用IDL(接口定义语言)进行  <br/>接口定义,如Protocol  <br/>Buffers、Thrift等。 |
| 跨语言性 | 支持跨语言通信,可以使用  <br/>HTTP作为通信协议实现不同语  <br/>言之间的通信。 | 支持跨语言通信,可以使用IDL  <br/>生成不同语言的客户端和服务  <br/>端代码。 |
| 灵活性 | 更加灵活,适用于不同类型的  <br/>应用场景,如Web开发、API调  <br/>用等。 | 更加高效,适用于需要高性能  <br/>和低延迟的分布式系统。 |
在微服务体系里：
- 基于HTTP风格的远程调用通常使用框架如Feign来实现
- 基于RPC的远程调用通常使用框架如Dubbo来实现。
**回答：**
HTTP和RPC主要区别在设计目的和使用场景上。HTTP是应用层协议，主要用于不同系统间的通信，像浏览器访问网站、前后端交互这些场景常用，一般用JSON或XML这种文本格式传数据，好处是简单通用，跨平台跨语言都方便，调试也容易，比如用curl就能发请求，但文本格式数据冗余多，传输效率稍低。RPC是远程过程调用，重点是让远程服务调用像本地方法调用一样，比如微服务里服务A调服务B的函数，通常用二进制协议，序列化快，传输效率高，适合内部服务间频繁通信，但需要两端提前约定接口，通用性不如HTTP。所以简单说，HTTP适合对外或跨平台通信，RPC适合内部服务高效调用。
### 什么是Feign？ 
**分析：**
Feign是一个声明式的Web服务客户端，它简化了使用基于HTTP的远程服务的开发。
Feign是在RestTemplate 和 Ribbon的基础上进一步封装，使用RestTemplate实现Http调用，使用Ribbon实现负载均衡。
Feign的主要特点和功能包括：
1. 声明式API：Feign允许开发者使用简单的注解来定义和描述对远程服务的访问。通过使用注解，开发者可以轻松地指定URL、HTTP方法、请求参数、请求头等信息，使得远程调用变得非常直观和易于理解。
2. 集成负载均衡：Feign集成了Ribbon负载均衡器，可以自动实现客户端的负载均衡。它可以根据服务名和可用实例进行动态路由，并分发请求到不同的服务实例上，提高系统的可用性和可伸缩性。
3. 容错机制：Feign支持集成Hystrix容错框架，可以在调用远程服务时提供容错和断路器功能。当远程服务不可用或响应时间过长时，Feign可以快速失败并返回预设的响应结果，避免对整个系统造成级联故障。
**回答：**
Feign是Spring Cloud里的声明式HTTP客户端，主要用来简化微服务之间的调用。之前用RestTemplate调用远程服务时，得自己拼URL、处理参数，写起来麻烦还容易出错。Feign就不一样，它让你通过定义接口加注解的方式来调用远程服务，比如用@FeignClient指定服务名，方法上用@RequestMapping这些注解定义请求路径和参数，调用的时候直接调这个接口的方法就行，不用管HTTP请求的具体细节，调用远程服务就像调用本地接口方法一样简单。而且Feign默认集成了Ribbon做负载均衡，结合注册中心能自动找到服务实例，还能和Hystrix集成做熔断降级，用起来方便，代码也更简洁。
### 为什么Feign第一次调用耗时很长？
**分析：**
主要原因是由于Ribbon的懒加载机制，当第一次调用发生时，Feign会触发Ribbon的加载过程，包括从服务注册中心获取服务列表、建立连接池等操作，这个加载过程会增加首次调用的耗时。
那怎么解决这个问题呢？
可以在应用启动时预热Feign客户端，自动触发一次无关紧要的调用，来提前加载Ribbon和其他相关组件。这样，就相当于提前进行了第一次调用。
**回答：**
Feign第一次调用耗时很长，主要是因为第一次调用时要完成一些必要的初始化工作。Feign基于接口生成动态代理对象，这个代理对象不是启动时就创建好的，而是第一次调用时才触发创建，过程中需要扫描接口信息、生成代理类，这会占用时间。另外Feign通常配合Ribbon做负载均衡，第一次调用时Ribbon得从服务注册中心拉取服务列表，获取可用的服务实例信息，这个网络请求和数据处理过程也需要时间。如果项目里启用了Hystrix，第一次调用还会初始化Hystrix的线程池、熔断器等资源。这些初始化操作叠加在一起，就导致第一次调用比后面的调用耗时明显更长。
### Fegin怎么做负载均衡？Ribbon?
**分析：**
在Feign中，负载均衡是通过集成Ribbon来实现的。
Ribbon是Netflix开源的一个客户端负载均衡器，可以与Feign无缝集成，为Feign提供负载均衡的能力。
Ribbon在发起请求前，会从“服务中心”获取服务列表（清单），然后按照一定的负载均衡策略去发起请求，从而实现客户端的负载均衡。Ribbon本身也维护着“服务提供者”清单的有效性。如果它发现“服务提供者”不可用，则会重新从“服务中心”获取有效的“服务提供者”清单来及时更新。
**回答：**
Fegin本身不直接处理负载均衡，它主要是简化服务调用的声明式客户端，实际的负载均衡功能是靠集成Ribbon来实现的。当用Fegin调用其他服务时，Ribbon会先从注册中心（像Eureka这类）获取目标服务的所有可用实例列表。拿到列表后，Ribbon会根据配置的负载均衡策略来选择一个具体的服务实例。常见的策略有轮询、随机、权重等，默认一般是轮询。选好实例后，Ribbon会把请求转发到这个实例上，这样就完成了负载均衡的过程。简单说就是Fegin负责定义调用接口，Ribbon负责找合适的服务实例并转发请求，两者配合实现负载均衡调用。
### Feign和Dubbo的区别呢？
**分析：**
需要注意的是，Feign和Dubbo并不是互斥的关系。实际上，Dubbo可以使用HTTP协议作为通信方式，而Feign也可以集成RPC协议进行远程调用。选择使用哪种远程调用方式取决于具体的业务需求和技术栈的选择。
**回答：**
Feign和Dubbo都是远程调用工具，但区别挺明显的。Feign是Spring Cloud生态里的，主要用HTTP协议，走RESTful接口，写起来就像调本地方法，加个注解就行，比较轻量，HTTP协议跨语言方便，Java和其他语言都能调。Dubbo是阿里的RPC框架，用的TCP协议，传输数据是二进制的，性能比Feign好，速度快。不过Dubbo主要是Java生态在用，接口定义得严格点，得先写个接口类。另外Dubbo自带服务治理功能，像注册中心、监控、容错这些都有，Feign本身功能简单，负载均衡得靠Ribbon这些组件配合。所以如果是Java内部服务，要高性能就选Dubbo；如果要跨语言或者用Spring Cloud生态，Feign更合适。
### Feign与OpenFeign的区别？
**分析：**
Feign是Netflix公司写的，是Spring Cloud组件中的一个轻量级RESTful的HTTP服务客户端；Feign内置了Ribbon，用来做客户端负载均衡，去调用服务注册中心的服务。Feign的使用方式是：使用Feign的注解定义接口，调用这个接口，就可以调用服务注册中心的服务。
```XML
<dependency>  
    <groupId>org.springframework.cloud</groupId>  
    <artifactId>spring-cloud-starter-feign</artifactId>
</dependency>
```
OpenFeign是SpringCloud自己研发的，在Feign的基础上支持了SpringMVC的注解，如@RequesMapping等等。OpenFeign的@FeignClient可以解析SpringMVC的@RequestMapping注解下的接口，并通过动态代理的方式产生实现类，实现类中做负载均衡并调用其他服务。
```XML
<dependency>  
    <groupId>org.springframework.cloud</groupId>  
    <artifactId>spring-cloud-starter-openfeign</artifactId>
</dependency>
```
**回答：**

### **Ribbon和 Feign 调用服务的区别是什么？**

**回答：**

## 服务容灾
### 什么是断路器？为什么需要断路器
**分析：**
在微服务架构中，服务之间形成调⽤链路，链路中的任何⼀个服务提供者都可能⾯临着相应超时、宕机等不可⽤的情况，在⾼并发的情况下，这种情况会随着并发量的上升恶化，形成“雪崩效应”，⽽断路器 正是⽤来解决这⼀个问题的组件。
断路器基本原理为： 
- 正常情况下，断路器关闭，服务消费者正常请求微服务 
- ⼀段事件内，失败率达到⼀定阈值（⽐如50%失败，或者失败了50次），断路器将断开，此时不再请求服务提供者，⽽是只是快速失败的⽅法（断路⽅法） 
- 断路器打开⼀段时间，⾃动进⼊“半开”状态，此时，断路器可允许⼀个请求⽅法服务提供者，如果请求调⽤成功，则关闭断路器，否则继续保持断路器打开状态。 
断路器保证了局部发⽣的错误，不会扩展到整个系统，从⽽保证系统的即使出现局部问题也不会造成系统雪崩。 
**回答：**
断路器是系统里用来监控服务调用的组件，当被调用的服务出问题，比如响应变慢或者频繁失败，它就会自动“断开”后续的请求，不让故障继续影响下去。
为什么需要呢？因为如果被调用的服务出故障了，调用方还一直发请求或者等着响应，会占用很多资源，像线程、连接这些，时间长了调用方自己也会出问题，甚至可能导致整个系统跟着崩溃。断路器能在这种时候快速返回结果，保护调用方不被拖垮，等被调用的服务恢复正常后，再慢慢恢复请求，这样就能避免故障扩散，让系统更稳定。
### 什么是**Hystrix？**
**分析：**
Hystrix是断路器的落地实现，防雪崩利器，具有服务降级，服务熔断，服务隔离，服务监控等功能。 
- 服务降级：对于查询操作, 可以实现⼀个fallback⽅法, 当请求下游服务出现异常的时候，使⽤ fallback⽅法返回的值，fallback⽅法的返回值⼀般是设置的默认值或者来⾃缓存。 
-  服务熔断：当请求下游服务失败数量超过⼀定⽐例(默认50%), 断路器会切换到开路状态(Open)， 这时所有请求会直接失败⽽不会发送到下游服务。断路器保持在开路状态⼀段时间后(默认5秒), ⾃ 动切换到半开路状态(HALF-OPEN)。这时会判断下⼀次请求的返回情况, 如果请求成功, 断路器切回闭路状态(CLOSED), 否则重新切换到开路状态(OPEN)。 
- 服务隔离：通过线程池（或信号量）来实现资源隔离，通常在使⽤的时候我们会根据调⽤的下游服务划分出多个线程池。例如调⽤产品服务的Command放⼊A线程池, 调⽤账户服务的Command放⼊B线程池，这样做的主要优点是运⾏环境被隔离开了。这样就算调⽤服务的代码存在bug或者由于其他原因导致⾃⼰所在线程池被耗尽时, 不会对系统的其他服务造成影响。 
- 服务监控：将服务执⾏结果和运⾏指标，请求数量成功数量等等这些状态进⾏收集，然后即可看到实时的监控数据。 
**回答：**
Hystrix是Netflix开源的一个工具，主要用在分布式系统里处理服务调用的故障问题。当我们的系统里有很多微服务互相调用时，要是某个依赖的服务出问题了，比如响应慢或者老失败，就可能拖垮整个调用链，导致级联故障。Hystrix就是来防止这种情况的。
它最核心的功能有三个。一是熔断，当调用某个服务失败的次数或者比例超过设定值，Hystrix会自动“切断”这个调用，不让新的请求再发过去，等服务恢复得差不多了再尝试连接，这样能避免故障扩散。二是降级，熔断的时候或者服务确实处理不过来，Hystrix会返回一个预设的简单结果，比如“当前服务忙，请稍后再试”，不让用户一直等着或者看到错误页面。三是隔离，它会把每个依赖服务的调用放在独立的线程池里，就算某个线程池里的服务调用出问题了，也不会占用其他服务的资源，保证系统整体还能正常跑。
平时在微服务架构里用得挺多，主要就是为了提高系统的稳定性，别因为一个小服务挂了就整个系统崩掉。
### 微服务雪崩效应是什么？
**分析：**
在微服务架构中，⼀个应⽤可能会有多个微服务组成，微服务之间的数据交互通过远程过程调⽤完成。 
假设微服务A调⽤微服务B和微服务C，微服务B和微服务C⼜调⽤其它的微服务，如果在调⽤链路上某个微服务的调⽤响应时间过⻓或者不可⽤，对微服务A的调⽤就会占⽤越来越多的系统资源，进⽽引起系统崩溃，所谓的“雪崩效应”。 
一般，为了防止服务雪崩，可以采用这些措施：
1. 服务高可用部署：确保各个服务都具备高可用性，通过冗余部署、故障转移等方式来减少单点故障的影响。
2. 限流和熔断：对服务之间的请求进行限流和熔断，以防止过多的请求涌入导致后端服务不可用。
3. 缓存和降级：合理使用缓存来减轻后端服务的负载压力，并在必要时进行服务降级，保证核心功能的可用性。
**回答：**
微服务雪崩效应就是微服务架构里，某个服务出问题后，依赖它的其他服务跟着出问题，最后整个系统都崩溃的情况。具体来说，比如一个核心服务突然响应慢或者直接挂了，调用它的服务如果没处理好，还在不停地发请求，这样调用方的资源就会被占满，像线程不够用、连接池耗尽之类的，导致调用方自己也没法处理新请求，接着依赖这些调用方的服务也会因为拿不到响应出问题，一环扣一环，最后整个系统可能就瘫了。简单说就是一个服务故障引发连锁反应，让整个系统跟着崩溃。
### 服务降级，你了解吗？
**分析：**
所谓降级，就是当某个服务熔断之后，服务器将不再被调用，此时客户端可以自己准备一个本地的fallback回调，返回一个缺省值。也可以理解为兜底方法。
会发生降级的情况：
- 程序运行异常
- 超时
- 服务熔断触发服务降级
- 线程池、信号量打满也会导致服务降级
**回答：**
服务降级我了解，简单讲就是系统压力大的时候，主动把一些非核心服务的功能或性能降一降，保证核心服务能正常运行。因为要是不这么做，高并发或者资源不够用的时候，所有服务挤在一起抢资源，可能整个系统都崩溃，核心功能也用不了。常见的做法就是关一些非核心功能，比如电商平台的商品推荐、用户评论这些，或者简化功能，比如只返回关键数据，不返回详细信息，也可以用缓存好的数据代替实时计算，减少服务器压力。主要目的就是在资源有限的时候，优先保障核心业务能正常用，让用户最需要的功能不受影响，让系统整体更稳定。
### 服务熔断，你了解吗？
**分析：**
在复杂的分布式系统中，微服务之间的相互调用，有可能出现各种各样的原因导致服务的阻塞，在高并发场景下，服务的阻塞意味着线程的阻塞，导致当前线程不可用，服务器的线程全部阻塞，导致服务器崩溃，由于服务之间的调用关系是同步的，会对整个微服务系统造成服务雪崩。
为了解决某个微服务的调用响应时间过长或者不可用进而占用越来越多的系统资源引起雪崩效应就需要进行服务熔断和服务降级处理。
所谓的服务熔断指的是某个服务故障或异常一起类似显示世界中的“保险丝"当某个异常条件被触发就直接熔断整个服务，而不是一直等到此服务超时。
服务熔断就是相当于我们电闸的保险丝，一旦发生服务雪崩的，就会熔断整个服务，通过维护一个自己的线程池，当线程达到阈值的时候就启动服务降级，如果其他请求继续访问就直接返回fallback的默认值。
**回答：**
服务熔断啊，我了解，它就是分布式系统里保护服务的一种机制。当一个服务调用失败次数太多，或者响应特别慢的时候，熔断机制就会触发。这时候它会暂时停止对这个服务的调用，不让故障继续扩散，避免影响到其他服务。熔断之后不是一直停着，它有个恢复过程。一开始是打开状态，拒绝所有请求；过一会儿会变成半打开状态，放少量请求过去试试。如果这些请求能成功，就恢复到正常的闭合状态，继续调用；要是还失败，就继续保持打开状态。这样就能防止单个服务故障导致整个系统雪崩，保证整体系统的稳定运行。
### 服务限流，你了解吗？
**分析：**
限流可以认为是服务降级的一种，限流就是限制系统的输入和输出流量以达到保护系统的目的。
一般来说系统的吞吐量是可以被测算的，为了保证系统的稳固运行，一旦达到的需要限制的阈值，就需要限制流量并采取少量措施以完成限制流量的目的。
比方：推迟解决，拒绝解决，或者部分拒绝解决等等。秒杀高并发等操作，严禁一窝蜂的一样拥挤，排队有序进行，一秒钟N个，有序进行。
**回答：**
服务限流就是控制单位时间内的请求数量，防止太多请求一下子打崩服务。主要是为了保护系统，尤其是高并发场景下比如秒杀、促销活动，请求量突然变大，不限流的话服务器可能扛不住，会出现响应变慢甚至直接宕机的情况。常见的方法有计数器，统计一段时间内的请求数，超过设定值就拒绝新请求；漏桶是按固定速度处理请求，多余的请求要么排队要么直接丢弃；令牌桶会按固定速度生成令牌，请求得拿到令牌才能处理，能应对一定的突发流量。实际使用时要结合业务选方法，比如实时性要求高的场景用令牌桶，需要严格控制处理速度的用漏桶。还要通过监控了解系统的承载能力，设置合适的限流阈值，通常不会单独用，一般和熔断、降级一起配合，比如限流后还是扛不住压力，就熔断部分非核心功能，保证核心服务能正常运行。
### **什么是降级熔断？为什么要进行熔断？**
**分析：**
熔断降级是一种分布式系统的保护机制，用于应对服务不稳定或不可用的情况。
- **熔断**是指当某个服务的调用失败次数或异常比例达到一定阈值时，自动切断对该服务的调用，让请求快速失败，避免影响其他服务而导致雪崩效应。熔断后，一段时间内不再调用该服务，直到服务恢复正常或者超过最大等待时间。
- **降级**是指当某个服务不可用或响应缓慢时，提供一个备用的处理逻辑，例如返回默认值、缓存值、错误提示等，以保证服务的可用性和容错性。降级可以在熔断时触发，也可以在其他情况下触发，例如系统负载过高、资源紧张等。
熔断降级的目的是为了保护系统的稳定性和可用性，防止故障扩散和蔓延，提高用户体验和信任度。
**回答：**
降级熔断是系统应对故障的两种常用机制。降级一般是系统压力大时主动降低功能或性能，比如简化返回数据、关闭非核心功能，优先保证核心服务运行。熔断则是当依赖的服务频繁出错时，暂时停止调用它，直接返回预设结果，不再让请求继续发送。
为什么要做熔断呢？主要是防止故障扩散。如果一个服务出问题，其他调用它的服务还在不停地发请求、重试，就会占用大量资源，比如线程、连接池，慢慢拖垮整个系统，导致服务雪崩。熔断能快速切断故障链路，让系统有时间恢复，避免连锁反应，保护整体稳定性。等依赖的服务恢复正常后，再重新放开调用。

### Hystrix怎么实现服务容错？
**分析：**
尽管已经不再更新，但是Hystrix是非常经典的服务容错开源库，它提供了多种机制来保护系统：
1. 服务熔断（Circuit Breaker）：Hystrix通过设置阈值来监控服务的错误率或响应时间。当错误率或响应时间超过预设的阈值时，熔断器将会打开，后续的请求将不再发送到实际的服务提供方，而是返回预设的默认值或错误信息。这样可以快速隔离故障服务，防止故障扩散，提高系统的稳定性和可用性。
2. 服务降级（Fallback）：当服务熔断打开时，Hystrix可以提供一个备用的降级方法或返回默认值，以保证系统继续正常运行。开发者可以定义降级逻辑，例如返回缓存数据、执行简化的逻辑或调用其他可靠的服务，以提供有限但可用的功能。
3. 请求缓存（Request Caching）：Hystrix可以缓存对同一请求的响应结果，当下次请求相同的数据时，直接从缓存中获取，避免重复的网络请求，提高系统的性能和响应速度。
4. 请求合并（Request Collapsing）：Hystrix可 以将多个并发的请求合并为一个批量请求，减少网络开销和资源占用。这对于一些高并发的场景可以有效地减少请求次数，提高系统的性能。
5. 实时监控和度量（Real-time Monitoring and Metrics）：Hystrix提供了实时监控和度量功能，可以对服务的执行情况进行监控和统计，包括错误率、响应时间、并发量等指标。通过监控数据，可以及时发现和解决服务故障或性能问题。
6. 线程池隔离（Thread Pool Isolation）：Hystrix将每个依赖服务的请求都放在独立的线程池中执行，避免因某个服务的故障导致整个系统的线程资源耗尽。通过线程池隔离，可以提高系统的稳定性和可用性。

Hystrix实现服务容错主要靠几个核心机制。首先是熔断，当调用某个服务的失败率或者超时次数达到设定阈值，就会触发熔断，这时候新请求会直接被拒绝，不再发往故障服务，等一段时间后再尝试恢复，避免故障扩散到整个系统。然后是降级，熔断触发或者请求超时的时候，不会返回错误，而是调用预设的降级方法，返回备用数据或者友好提示，保证用户能拿到响应，不影响主流程。还有线程隔离，它会给每个依赖服务分配独立的线程池，这样就算某个服务出问题把自己的线程池占满了，也不会影响其他服务的线程资源，防止整个系统的线程被耗尽。另外还有超时控制，每个请求都设置超时时间，超过时间就主动中断，不让请求一直阻塞占用资源。这些机制一起作用，就能在服务出问题时保护系统，实现容错。
### **Sentinel 是什么？它是如何工作的？**
**分析：**
Sentinel 是阿里巴巴开源的一款分布式服务架构的轻量级流量控制产品，它主要以流量为切入点，从流量控制、熔断降级、系统负载保护等多个维度来帮助您保护服务的稳定性。
Sentinel 的基本概念包括资源、规则和处理器。资源是 Sentinel 的关键概念，可以是 Java 应用程序中的任何内容，例如由应用程序提供的服务，或由应用程序调用的其它应用提供的服务，甚至可以是一段代码。规则是围绕资源的实时状态设定的，可以包括流量控制规则、熔断降级规则以及系统保护规则，所有规则可以动态实时调整。
Sentinel 的主要功能有：
1. **流量控制**：Sentinel 可以控制每个服务或接口的并发请求数量，避免因为并发请求过多导致服务崩溃。
2. **熔断降级**：当某个服务或接口不可用时，Sentinel 可以自动触发熔断机制，避免因单个服务或接口故障导致整个系统的瘫痪。
3. **系统负载保护**：Sentinel 通过控制系统的整体负载，避免因系统过载导致服务性能下降甚至崩溃。
Sentinel 的工作原理主要分为三个步骤：
1. **数据采集**：Sentinel 通过代理模式将流量数据采集到自身，并进行数据清洗和整合。
2. **策略计算**：根据预先设定的规则和算法，Sentinel 计算并判断是否需要控制流量、熔断降级或保护系统负载。
3. **结果执行**：根据计算结果，Sentinel 对流量进行控制、熔断降级或保护系统负载等操作，以保障服务的稳定性。
总之，Sentinel 作为一款轻量级流量控制产品，适用于各种分布式服务架构，能够帮助您有效地保护服务的稳定性，提高系统的可用性和容错性。
**回答：**
Sentinel是阿里巴巴开源的流量控制工具，主要用来保护微服务系统，避免因流量异常导致服务不可用。它的工作流程是这样的：首先会实时监控系统流量，比如接口的QPS、并发请求数这些数据。然后根据预设的规则，像限流、熔断、降级这些，当流量达到规则里的阈值时，就触发对应的控制策略。比如限流会限制每秒最多通过多少请求，超出的直接拒绝或排队；熔断是如果接口出错率太高，暂时不让新请求进来，等恢复后再放开；降级可能返回缓存数据或默认值，保证服务还能响应。这样就能在流量高峰时保护核心资源，让系统更稳定。
### Sentinel怎么实现限流的？
**分析：**
Sentinel通过动态管理限流规则，根据定义的规则对请求进行限流控制。具体实现步骤如下：
- 定义资源：在Sentinel中，资源可以是URL、方法等，用于标识需要进行限流的请求。
```Java
// 原本的业务方法.
@SentinelResource (blockHandler = "blockHandlerForGetUser")
public User getUserById(String id) {
    throw new RuntimeException("getUserById command failed");
}
// blockHandler 函数，原方法调用被限流/降级/系统保护的时候调用
public User blockHandlerForGetUser(String id, BlockException ex) {
    return new User("admin");
}
```
- 配置限流规则：在Sentinel的配置文件中定义资源的限流规则。规则可以包括资源名称、限流阈值、限流模式（令牌桶或漏桶）等。
```Java
private static void initFlowQpsRule() {
    List<FlowRule> rules = new ArrayList<>();    FlowRule rule1 = new FlowRule();  // 创建一个流控规则
    rule1.setResource(resource);   // 设置要限流的资源名称
    rule1.setCount(20);  // 设置最大 QPS 为 20
    rule1.setGrade(RuleConstant.FLOW_GRADE_QPS);  // 设置限流的维度为 QPS
    rule1.setLimitApp("default");  // 设置限制的应用名称为 "default"
    rules.add(rule1);  // 将规则添加到规则列表中
    FlowRuleManager.loadRules(rules);  // 加载规则列表，使限流规则生效
}
```
- 监控流量：Sentinel会监控每个资源的流量情况，包括请求的QPS（每秒请求数）、线程数、响应时间等。
- 限流控制：当请求到达时，Sentinel会根据资源的限流规则判断是否需要进行限流控制。如果请求超过了限流阈值，则可以进行限制、拒绝或进行其他降级处理。
**回答：**
Sentinel实现限流大概是这么个流程：先得配个限流规则，比如你想限制每秒最多100个请求，或者同时最多50个并发请求，这些规则里得写清楚阈值和类型。然后它会实时盯着请求，比如统计QPS的话，就按时间窗口算每秒进来多少请求；统计并发数的话，就看当前同时在处理的请求有多少。接着它会拿实时统计的数和规则里的阈值比，要是超过了，就触发限流。限流的时候，一般是直接拒绝新请求，也可以让请求排队等会儿，或者降级返回个默认结果，比如“系统繁忙”。核心就是靠规则定义、实时统计、阈值判断、执行限流策略这几步，保证服务不会被太多请求冲垮。
### Sentinel采用的什么限流算法？
**分析：**
Sentinel使用滑动窗口限流算法来实现限流。
滑动窗口限流算法是一种基于时间窗口的限流算法。它将一段时间划分为多个时间窗口，并在每个时间窗口内统计请求的数量。通过动态地调整时间窗口的大小和滑动步长，可以更精确地控制请求的通过速率。
**回答：**
Sentinel主要采用的限流算法有令牌桶算法、漏桶算法和滑动窗口算法。令牌桶算法就是系统按固定速率生成令牌，请求过来时需要获取令牌才能处理，这样能控制请求的平均速率，还允许一定程度的突发流量。漏桶算法是让请求像水流进桶里，桶再按固定速率把请求漏出去处理，不管进来的流量多快，出去的速度始终稳定，能防止突发流量冲击系统。滑动窗口算法是把时间分成多个小的时间窗口，实时统计每个窗口内的请求数量，相比固定窗口统计更精准，能避免在窗口切换时出现流量峰值的问题。这几种算法结合使用，让Sentinel能根据不同场景灵活控制流量，既保证系统稳定又能合理利用资源。
### Sentinel怎么实现集群限流？
**分析：**
Sentinel利用了Token Server和Token Client的机制来实现集群限流。
开启集群限流后，Client向Token Server发送请求，Token Server根据配置的规则决定是否限流
**回答：**
Sentinel集群限流主要是为了控制分布式系统的整体流量，避免每个节点单独限流时总和超过预期。它的实现核心是分服务端和客户端模式。服务端叫Token Server，负责统一管理限流规则和令牌发放，客户端是业务服务节点，每次需要限流时会先向服务端请求令牌。客户端和服务端通过网络通信，服务端根据配置的规则（比如QPS阈值）判断是否给令牌，返回结果后客户端再决定放不放行。如果客户端连不上服务端，会降级用本地限流兜底，避免完全不可用。为了高可用，服务端可以集群部署，通过注册中心选主节点，保证不会因为单个服务端故障影响整个集群限流。这样就能实现整个分布式系统的统一限流控制了。
### **Sentinel 与Hystrix的区别是什么？**
**分析：**
Hystrix和Sentinel都是微服务架构中实现熔断和限流的工具，它们有以下区别和特点：
- **Hystrix是Netflix开源的熔断器实现，主要用于保护分布式系统中的服务调用**。它的主要特点包括线程隔离、资源保护和降级处理。Hystrix通过将每个服务调用放入独立的线程池中来实现线程隔离，防止一个服务的延迟或故障影响其他服务。它通过监控服务调用的成功率、延迟等指标来保护后端资源，并在失败的请求或响应超时达到一定阈值时自动打开熔断器，避免连锁故障。此外，Hystrix还提供了降级处理功能，可以在服务不可用或响应过慢时返回预定义的降级响应，保证系统的可用性。
- **Sentinel是阿里巴巴开源的流量控制和系统保护工具，主要用于实现微服务架构中的流量控制、熔断、降级和系统负载保护等**。它的主要特点包括实时监控和动态规则配置、丰富的流量控制策略、细粒度的服务保护以及支持多种编程语言。Sentinel可以实时监控服务的请求流量和各项指标，并提供实时的仪表盘和可视化的监控界面。它还支持通过API动态配置流量控制和熔断规则，可以根据实际情况进行动态调整。Sentinel提供了多种流量控制策略，包括基于QPS、线程数、并发连接数等多种指标进行的流量控制。此外，Sentinel还支持对每个具体的服务接口进行熔断、降级和限流等操作，以实现精确的服务保护策略。同时，Sentinel不仅支持Java，还支持Go、Python等多种编程语言，使其适用于跨语言的微服务架构。
总的来说，Hystrix注重线程隔离和资源保护，适用于保护单个服务调用。而Sentinel注重流量控制和动态规则配置，适用于对整个系统的流量进行监控和保护。根据实际需求和技术栈，可以选择适合的工具来实现微服务架构中的熔断和限流功能。
**回答：**
Sentinel和Hystrix都是服务容错工具，但区别还挺明显的。Hystrix是Netflix的，现在基本不更新了，Sentinel是阿里的，还在活跃维护。功能上Hystrix主要做熔断降级，Sentinel除了这个，还强调实时流量控制，像限流、熔断、降级都支持，功能更全面些。配置方面Sentinel支持动态调整规则，改了不用重启服务，Hystrix配置相对固定，调整得重启。监控上Sentinel自带控制台，能实时看流量、熔断状态这些数据，Hystrix得配合Turbine之类的工具才能看聚合监控。适用场景的话，如果系统需要细粒度的流量控制和动态配置，选Sentinel更合适；要是简单的熔断降级需求，Hystrix也行，但现在实际项目里用Sentinel的更多些，毕竟维护和功能都占优势。
## 服务网关
### 什么是服务网关？为什么需要服务网关？
**分析：**
在分布式系统中，服务之间相互依赖，服务调用链路通常比较复杂，同时服务的部署和变化也非常频繁。服务网关的作用就是解决这个问题。
服务网关是一种在服务调用链路上增加一个中间件的机制，它可以将多个服务的调用进行统一入口和出口的管理，从而简化服务的调用和管理。服务网关通常具有如下功能:
- 路由转发:服务网关可以通过路由转发的方式将请求分发到不同的服务实例上，从而实现负载均衡和流量控制的功能。
- 安全防护:服务网关可以实现身份认证、授权、加密等安全防护功能，保障服务的安全性和可靠性。
- 缓存加速:服务网关可以通过缓存加速的方式提高服务的响应速度和性能。
- 协议转换: 服务网关可以实现协议的转换，例如将 HTTP 协议转换成 HTTPS 协议。
- 日志监控:服务网关可以实现请求的日志监控和统计，方便开发者了解服务的使用情况和性能指标。
Spring Cloud 通过 Zuul、Gateway 等组件实现了服务网关，它可以带来以下好处:
- 简化调用:通过服务网关，可以将多个服务的调用进行统一入口和出口的管理，从而简化服务的调用和管理。
- 提高可靠性:通过服务网关，可以实现负载均衡、流量控制、安全防护等功能，从而提高服务的可靠性和稳定性。
- 提高性能:通过服务网关，可以实现缓存加速、协议转换等功能，从而提高服务的响应速度和性能。
- 简化配置:通过使用服务网关，可以简化服务的配置和管理，从而降低系统的维护成本。
**回答：**
服务网关其实就是客户端和后端微服务之间的一个中间层，所有客户端请求都会先经过网关，再由网关转发给对应的微服务。为什么需要呢？首先是统一入口，微服务多的时候，客户端不用记每个服务的地址，直接调网关就行，方便管理。然后是路由转发，网关能根据请求路径把请求转到正确的服务，不用客户端自己判断。认证授权也很关键，用户登录信息验证这些，网关统一做了，各个微服务就不用重复开发。限流熔断也不能少，请求太多或者某个服务出问题时，网关能限制请求量或者熔断故障服务，保护系统不被拖垮。监控日志也能通过网关统一收集，方便排查问题。所以服务网关主要解决微服务架构里的入口管理、安全、稳定性问题，让系统更好维护。

### **什么是限流算法，网关如何实现限流？**
**分析：**
限流算法是指用于限制单位时间内服务的请求数量的算法，目的是防止服务被过高的请求压力所击垮。常见的限流算法包括**计数器算法、滑动窗口算法、漏桶算法、令牌桶算法**。
网关如何实现限流：
1. **利用限流算法插件/模块**：网关可以集成限流算法插件/模块，通过配置相关参数（如令牌桶大小、令牌生成速率等）来实现限流。例如，Spring Cloud Gateway可以使用Redis的RateLimiter限流算法插件来实现限流。
2. **自定义限流逻辑**：网关可以通过编程方式自定义实现限流逻辑。例如，在微服务架构中，可以在每个服务的网关层（如Zuul等）实现限流逻辑，或者使用限流SDK（如Sentinel）对请求进行限流。
3. **利用云平台提供的限流功能**：一些云平台提供了自动化的限流功能，例如AWS CloudWatch、Azure Application Insights等，网关可以利用这些云平台的功能来实现限流。
**回答：**
限流算法就是控制单位时间内请求数量的方法，防止系统被过多请求压垮。常见的有固定窗口，比如1秒最多处理100个请求；滑动窗口是把固定窗口分成更小的时间段，让限流更平滑；漏桶是让请求匀速处理，像漏斗漏水一样稳定；令牌桶按固定速度生成令牌，请求拿到令牌才能处理，能应对突发流量。
网关实现限流，就是在请求进入系统前拦截检查。先确定限流对象，比如按IP、用户ID或者接口地址。然后选合适的算法，比如用令牌桶处理有突发需求的接口，设好每秒生成多少令牌的阈值。拦截到请求时，检查对应的限流对象是否超过阈值，超了就直接返回限流响应，比如429状态码。现在网关工具像Spring Cloud Gateway可以用Redis加Lua脚本实现分布式限流，Nginx也有limit_req模块直接配置限流，不用自己写太多代码。
### 什么是Spring Cloud Zuul?
**分析：**
Zuul微服务⽹关是为Spring Cloud Netflix提供认证鉴权、监控、动态路由、限流、压⼒测试等服务的框架，可以和Eureka、Ribbon、Hystrix等组件配合使⽤。 
主要功能 
- 认证鉴权：识别每个资源的验证要求，并拒绝那些与要求不符的请求。 
- 监控：追踪有意义的数据和统计结果，带来精确的⽣产视图。 
- 动态路由：动态地将请求路由到不同的后端集群。 
- 限流：为每⼀种负载类型分配对应容量，并弃⽤超出限定值的请求。

**回答：**
Spring Cloud Zuul是Spring Cloud里的网关组件，主要用作微服务架构的统一入口。它最核心的作用是路由转发，就是把前端发来的请求转到对应的后端服务，比如访问/api/user就转发到用户服务，不用前端记每个服务的具体地址。另外它还有过滤器功能，能统一处理一些公共逻辑，像认证授权，检查请求有没有合法token，没有就直接拦住；或者做限流，防止某个服务被太多请求冲垮；还能记录请求日志这些。它一般会和服务注册中心比如Eureka一起用，通过服务名就能找到对应服务地址，不用手动配IP端口。这样整个系统对外只有一个入口，管理起来方便，公共逻辑也不用每个服务重复写，用起来挺省事的。
### 什么是Spring Cloud Gateway?

**回答：**
Spring Cloud Gateway是Spring Cloud生态里的网关组件，主要用来统一处理客户端发过来的请求，然后转发到对应的微服务上。它的核心功能有路由转发，就是按配置的规则把请求转到不同服务；还能做负载均衡，把请求分到多个服务实例上；也支持熔断和限流，避免后端服务被太多请求压垮。它是基于Spring生态的，用了Netty和WebFlux，属于异步非阻塞的，性能比之前的Zuul网关好一些。在微服务架构里，它就像个统一入口，能集中处理认证、日志这些通用逻辑，让后端服务不用再单独处理这些，更专注自己的业务功能。
### Spring Cloud Gateway核心概念？
**分析：**
在Spring Cloud Gateway里，有三个关键组件：
- **Route（路由）**：路由是Spring Cloud Gateway的基本构建块，它定义了请求的匹配规则和转发目标。通过配置路由，可以将请求映射到后端的服务实例或URL上。路由规则可以根据请求的路径、方法、请求头等条件进行匹配，并指定转发的目标URI。
- **Predicate（断言）**：断言用于匹配请求的条件，如果请求满足断言的条件，则会应用所配置的过滤器。Spring Cloud Gateway提供了多种内置的断言，如Path（路径匹配）、Method（请求方法匹配）、Header（请求头匹配）等，同时也支持自定义断言。
- **Filter（过滤器）**：过滤器用于对请求进行处理和转换，可以修改请求、响应以及执行其他自定义逻辑。Spring Cloud Gateway提供了多个内置的过滤器，如请求转发、请求重试、请求限流等。同时也支持自定义过滤器，可以根据需求编写自己的过滤器逻辑。
又有两个比较重要的概念：
- **Gateway Handler（网关处理器）**：网关处理器是Spring Cloud Gateway的核心组件，负责将请求转发到匹配的路由上。它根据路由配置和断言条件进行路由匹配，选择合适的路由进行请求转发。网关处理器还会依次应用配置的过滤器链，对请求进行处理和转换。
- **Gateway Filter Chain（网关过滤器链）**：网关过滤器链由一系列过滤器组成，按照配置的顺序依次执行。每个过滤器可以在请求前、请求后或请求发生错误时进行处理。过滤器链的执行过程可以修改请求、响应以及执行其他自定义逻辑。
**回答：**
Spring Cloud Gateway是微服务架构里的网关组件，主要负责请求路由和跨切面处理。核心概念有三个：路由、断言、过滤器。路由是基础，定义了请求该转发到哪个服务，包含唯一ID、目标服务地址，还有断言和过滤器的集合。断言就是匹配规则，用来判断请求要不要走这个路由，比如看请求路径是不是/api开头、请求方法是不是GET、有没有带某个请求头等，匹配上了才会转发。过滤器用来处理请求和响应，能改请求头、加参数，或者做认证、限流这些操作，分全局过滤器对所有路由生效，和局部过滤器只对特定路由生效。它底层用WebFlux，是响应式的，支持异步非阻塞，性能比传统网关好。整体就是通过路由把请求导到对应服务，用断言判断能不能导，过滤器在中间做额外处理。
### 为什么我们选择GateWay？
**分析：**
1）因为Zuul1.0已经进入了维护阶段，而且Gateway是SpringCloud团队研发的，值得信赖，Gateway是基于异步非阻塞模型上进行开发的，性能方面不需要担心。虽然Netflix早就发布了最新的 Zuul 2.x，但 Spring Cloud 貌似没有整合计划。而且Netflix相关组件都宣布进入维护期，不知道前景如何。
2）Spring Cloud GateWay有很多特性
- 基于Spring Framework 5, Project Reactor 和 Spring Boot 2.0 进行构建；
- 动态路由：能够匹配任何请求属性；
- 可以对路由指定 Predicate（断言）和 Filter（过滤器）；
- 集成Hystrix的断路器功能；
- 集成 Spring Cloud 服务发现功能；
- 易于编写的 Predicate（断言）和 Filter（过滤器）；
- 请求限流功能；
- 支持路径重写。
**回答：**
我们选择Gateway主要是因为项目里微服务多，需要一个统一的入口来管理。之前每个服务直接对外，接口地址乱七八糟，前端调用起来麻烦，我们自己维护也费劲。用Gateway的话，所有请求先经过它，再转发到对应的服务，入口统一了，管理和维护都方便很多。
另外，Gateway能直接处理一些通用功能，比如路由转发、负载均衡，不用每个服务自己开发。像负载均衡，它能自动把请求分到不同的服务实例上，避免某个实例压力太大，系统稳定性提高不少。还有安全这块，认证授权、限流这些，统一在Gateway做，不用每个服务单独写，开发效率高，也减少了重复代码。
而且Gateway性能还行，处理请求快，不会拖慢整个系统。综合下来，它能解决我们微服务架构里入口管理、通用功能复用、系统稳定性这些实际问题，所以就选了它。
### Spring Cloud Gateway 与 Zuul的区别？
**分析：**
1）Zuul 1.x是一个基于阻塞 I/O 的 API Gateway
2）Zuul 1.x 基于Servlet 2.5使用阻塞架构，它不支持任何长连接(如 WebSocket)。Zuul的设计模式和Nginx较像，每次 I/O 操作都是从工作线程中选择一个执行，请求线程被阻塞到工作线程完成，但是差别是Nginx 用C++ 实现，Zuul 用 Java 实现，而 JVM 本身会有第一次加载较慢的情况，使得Zuul 的性能相对较差。
3）Zuul 2.x理念更先进，是基于Netty非阻塞和支持长连接的，但SpringCloud目前还没有整合。Zuul 2.x的性能较Zuul 1.x有较大提升。
4）Spring Cloud Gateway 建立在Spring Framework 5、Project Reactor和Spring Boot 2之上，使用非阻塞API。
5）Spring Cloud Gateway 还支持 WebSocket， 并且与Spring紧密集成拥有更好的开发体验。
**回答：**
Zuul是Netflix开发的，早期在Spring Cloud里用得多，它是基于Servlet的，底层用的是阻塞IO，处理请求的时候性能一般。后来Spring自己出了Gateway，它是基于Netty的，用的是非阻塞IO，响应式编程，所以处理请求的性能比Zuul好不少。另外，Gateway和Spring生态集成得更好，像Spring Boot Actuator、Spring Security这些组件用起来很方便，配置也简单。Zuul 1.x功能比较基础，想扩展功能的话会麻烦点。虽然Zuul后来出了2.x版本，也改成非阻塞了，但出来得晚，现在Spring Cloud里基本都主推Gateway，社区支持也更好，实际项目里用Gateway的更多。
### Spring Cloud GateWay工作流程？
**分析：**
- 客户端向 Spring Cloud Gateway 发出请求。然后在 Gateway Handler Mapping 中找到与请求相匹配的路由，将其发送到 Gateway Web Handler。
- Handler 再通过指定的过滤器链来将请求发送到我们实际的服务执行业务逻辑，然后返回。
- 过滤器之间用虚线分开是因为过滤器可能会在发送代理请求之前（“pre”）或之后（“post”）执行业务逻辑。
- Filter在“pre”类型的过滤器可以做参数校验、权限校验、流量监控、日志输出、协议转换等，在“post”类型的过滤器中可以做响应内容、响应头的修改，日志的输出，流量监控等。
核心逻辑：**路由转发+执行过滤链**
**回答：**
Spring Cloud Gateway的工作流程大概是这样：客户端发请求过来，先到Gateway。Gateway收到请求后，会根据请求的路径、方法这些信息，去匹配配置好的路由规则。路由规则里写着要转发到哪个目标服务。匹配到路由之后，会经过一系列过滤器处理。过滤器分两种，前置的在请求转发前处理，比如检查认证、做限流；后置的在服务返回响应后处理，比如改响应头。处理完前置过滤器，Gateway就把请求转发给目标服务。服务处理完请求返回响应，再经过后置过滤器，最后Gateway把响应返回给客户端。整个过程就是接收请求、匹配路由、过滤处理、转发请求、返回响应这几步。
## 配置中心
### 什么是配置中心？为什么需要配置中心？
**分析：**
在分布式系统中，服务通常需要配置一些参数和属性，例如数据库连接、缓存配置、日志级别等。这些配置可能会因为环境、版本、部署等原因而发生变化，手动管理和部署这些配置会变得非常困难和繁琐。配置中心的作用就是解决这个问题。
配置中心是一种统一管理和动态刷新配置的机制，它可以将配置信息集中存储在一个中心化的存储库中，例如 Git、SVN、ZooKeeper 等。当配置信息发生变化时，配置中心可以自动通知服务实例更新配置，并且支持动态刷新配置，无需重启服务实例。这样，就可以简化配置的管理和部署，提高系统的可维护性和稳定性。
Spring Cloud 通过 Config Server 实现了配置中心，它可以带来以下好处：
- 集中管理:通过配置中心，可以将所有服务的配置信息集中管理，避免了手动管理的复杂性和错误。2.动态刷新:通过配置中心，可以实现配置的动态刷新，无需重启服务实例，从而提高系统的可维护性和稳定性。
- 版本管理:通过配置中心，可以实现配置信息的版本管理，方便追踪和管理配置信息的变化。
- 安全管理:通过配置中心，可以实现配置信息的安全管理，例如加密、权限控制等。
- 简化配置:通过使用配置中心，可以简化配置的管理和部署，从而降低系统的维护成本。
**回答：**
配置中心其实就是集中管理项目里各种配置的地方。项目运行时需要很多配置，像数据库连接地址、服务端口、接口开关这些，以前这些配置可能散在每个服务的本地文件里，改配置的时候得找到每个服务手动改，改完还得重启服务才能生效，特别麻烦。而且不同环境的配置容易弄混，比如开发环境和生产环境的数据库地址不一样，手动管理容易出错。
用配置中心的话，所有配置都集中存在一起，改配置直接在配置中心操作就行，服务能自动获取最新配置，不用重启服务，效率高很多。另外还能统一管理不同环境的配置，给开发、测试、生产环境分别配不同的配置，不容易乱。敏感配置还能加密存储，比存在本地文件里安全。所以现在稍微大点的项目基本都会用配置中心，主要就是为了方便改配置、不用重启服务、统一管理环境配置，减少出错，提高效率。
### SpringCloud可以选择哪些配置中心？
**分析：**
和注册中心一样，SpringCloud也支持对多种配置中心的集成。常见的配置中心选型包括：
1. Spring Cloud Config：官方推荐的配置中心，支持将配置文件存储在Git、SVN等版本控制系统中，并提供RESTful API进行访问和管理。
2. ZooKeeper：一个开源的分布式协调服务，可以用作配置中心。它具有高可用性、一致性和通知机制等特性。
3. Consul：另一个开源的分布式服务发现和配置管理工具，也可用作配置中心。支持多种配置文件格式，提供健康检查、故障转移和动态变更等功能。
4. Etcd：一个分布式键值存储系统，可用作配置中心。它使用基于Raft算法的一致性机制，提供分布式数据一致性保证。
5. Apollo：携程开源的配置中心，支持多种语言和框架。提供细粒度的配置权限管理、配置变更通知和灰度发布等高级特性，还有可视化的配置管理界面。
6. Nacos：阿里巴巴开源的服务发现、配置管理和服务管理平台，也可以作为配置中心使用。支持服务注册与发现、动态配置管理、服务健康监测和动态DNS服务等功能。
**回答：**
SpringCloud常用的配置中心主要有三个。首先是Spring Cloud Config，这是官方提供的，基于Git仓库存储配置，支持版本控制，但要动态刷新配置的话得配合消息总线比如Spring Cloud Bus。然后是Spring Cloud Alibaba Nacos，阿里的组件，既能当注册中心又能做配置中心，支持动态配置实时生效，使用起来比较方便，现在很多项目都在用。还有携程的Apollo，配置管理功能很全，支持灰度发布、权限控制这些，界面也友好，适合配置比较复杂的场景。实际项目里选哪个，主要看团队熟悉度和项目需求，小项目用Nacos简单，复杂配置场景可能Apollo更合适。

### Nacos配置中心的原理了解吗？
**分析：**
配置中心，说白了就是一句话：配置信息的CRUD。
具体的实现大概可以分成这么几个部分：
1. 配置信息存储：Nacos默认使用内嵌数据库Derby来存储配置信息，还可以采用MySQL等关系型数据库。
2. 注册配置信息：服务启动时，Nacos Client会向Nacos Server注册自己的配置信息，这个注册过程就是把配置信息写入存储，并生成版本号。
3. 获取配置信息：服务运行期间，Nacos Client通过API从Nacos Server获取配置信息。Server根据键查找对应的配置信息，并返回给Client。
4. 监听配置变化：Nacos Client可以通过注册监听器的方式，实现对配置信息的监听。当配置信息发生变化时，Nacos Server会通知已注册的监听器，并触发相应的回调方法。
**回答：**
Nacos配置中心主要是帮应用管理配置的，能让配置和代码分开，还能动态更新不用重启应用。客户端启动的时候会连接Nacos服务端，拉取自己需要的配置，拉的时候会带上当前配置的版本。服务端这边把配置存在数据库里，可能还有缓存来加快访问速度。客户端拿到配置后会在本地存一份，同时和服务端保持长连接监听。等服务端的配置有更新，比如用户在控制台改了配置，服务端会先更新数据库和缓存，然后通过长连接通知客户端。客户端收到通知后就会去拉新的配置，更新本地存储，这样应用就能直接用新配置了，整个过程不用重启应用。
### Nacos配置中心长轮询机制？
**分析：**
一般来说客户端和服务端的交互分为两种：推（Push）和拉（Pull），Nacos在Pull的基础上，采用了长轮询来进行配置的动态刷新。
在长轮询模式下，客户端定时向服务端发起请求，检查配置信息是否发生变更。如果没有变更，服务端会"hold"住这个请求，即暂时不返回结果，直到配置发生变化或达到一定的超时时间。
- 如果客户端发起 **Pull** 请求，服务端收到请求之后，先检查配置是否发生了变更：
- **变更**：返回变更配置；
- **无变更**：设置一个定时任务，延期 29.5s 执行，把当前的客户端长轮询连接加入 allSubs 队列；
- 在这 29.5s 内的配置变化：
- **配置无变化**：等待 29.5s 后触发自动检查机制，返回配置；
- **配置变化**：在 29.5s 内任意一个时刻配置变化，会触发一个事件机制，监听到该事件的任务会遍历 allSubs 队列，找到发生变更的配置项对应的 ClientLongPolling 任务，将变更的数据通过该任务中的连接进行返回。相当于完成了一次 **PUSH** 操作；
- 长轮询机制结合了 **Pull** 机制和 **Push** 机制的优点；
通过长轮询的方式，Nacos客户端能够实时感知配置的变化，并及时获取最新的配置信息。同时，这种方式也降低了服务端的压力，避免了大量的长连接占用内存资源。
**回答：**
Nacos配置中心的长轮询机制，简单说就是客户端拉取配置时，服务器不会立刻返回结果。客户端发起请求后，服务器先检查配置是否有变更，没变更的话就把请求挂起，进入等待状态，默认等30秒左右。这期间如果配置更新了，服务器会马上唤醒请求，把新配置返回给客户端；要是等超时了配置还没变，就返回空结果。客户端收到结果后，不管是新配置还是空的，都会立刻再发一次长轮询请求。这样既能保证配置变更时客户端及时感知，又避免了短轮询频繁请求的资源浪费，是Nacos实现配置实时同步的主要方式。
## 链路跟踪
### 为什么要用微服务链路追踪？
**分析：**
在微服务中，有的上下游可能有十几个服务，如果某一环出了问题，排查起来非常困难，所以，就需要进行链路追踪，来帮助排查问题。

**回答：**
微服务拆分后服务数量多，一个用户请求可能要经过好几个服务才能完成。这时候要是出问题了，比如响应慢或者报错，光看单个服务日志根本找不着哪儿出了问题。链路追踪就是把请求经过的每个服务都记下来，从哪来、到哪去、每个服务花了多久，都能看得清清楚楚。这样排查问题的时候就能直接定位到具体哪个服务有问题，不用一个个服务去猜。另外，系统跑久了，哪些服务之间依赖关系复杂，哪个服务耗时太长拖慢整体性能，链路追踪也能帮着看出来，方便做优化。还有就是能实时监控请求状态，要是哪个环节超时或者出错了，能及时发现，避免影响用户。

## 分布式事务
### **什么情况下需要用到分布式事务？有哪些方案？**
**分析：**
分布式事务是指在多个网络节点或服务之间进行数据一致性处理的情况。以下是一些可能需要使用分布式事务的场景：
1. 微服务之间通过远程调用完成事务操作：当不同的微服务之间需要进行数据一致性保证时，就需要使用分布式事务。例如，一个电商微服务中的订单服务和库存服务需要通过远程调用进行事务操作，保证库存数量和订单信息的同步更新，避免出现超卖或缺货的情况。
2. 单体系统访问多个数据库实例：当一个系统需要访问多个数据库实例时，例如用户信息和订单信息分别存储在两个不同的数据库实例中，需要通过分布式事务保证数据一致性，避免出现数据不一致的情况。
3. 多服务访问同一个数据库实例：当多个服务访问同一个数据库实例时，例如订单微服务和库存微服务都需要访问同一个数据库，也可能需要使用分布式事务。因为跨JVM进程的多个服务同时持有不同的数据库连接进行数据库操作，可能会出现数据不一致的情况。
在这些场景下，我们需要使用分布式事务来保证数据的一致性。常用的分布式事务方案包括两阶段提交（2PC）、三阶段提交（3PC）、TCC、Saga、本地消息表等。其中，两阶段提交和三阶段提交都是基于锁机制实现的，而TCC、Saga和本地消息表则是基于业务逻辑实现的。选择哪种方案取决于业务需求、系统复杂性和性能等多个因素
**回答：**
当多个服务或数据库的操作需要一起成功或失败时就得用分布式事务，比如下单时要同时扣库存、减余额、生成订单，这些操作不能只成功一部分。常见方案有几种，2PC是两阶段提交，协调者先让各参与者准备，都准备好再统一提交，实现简单但性能差。TCC是把业务拆成Try、Confirm、Cancel三步，自己写确认和补偿逻辑，灵活但开发量大。Saga按步骤执行事务，失败了调用对应补偿操作，适合长事务场景。本地消息表是每个服务本地记录消息，通过消息队列异步通知其他服务，保证最终一致，实现简单但可能有延迟。
### **什么是Seata？谈谈你对Seata的理解？**
**分析：**
**Seata是一款开源的分布式事务解决方案**，它主要用于解决在分布式系统中全局事务的一致性问题。
在分布式系统中，由于一次业务操作需要跨多个数据源或进行远程调用，往往会产生分布式事务问题。例如，在一个电商微服务系统中，订单服务和库存服务需要协同工作，如果订单服务已经创建成功，但库存服务因为某些原因失败了，就会导致数据不一致的问题。Seata就是为解决这个问题而产生的。
Seata的主要特点是无侵入以及高性能。它对业务无侵入，可以减少技术架构上的微服务化所带来的分布式事务问题对业务的侵入，同时高性能则是减少分布式事务解决方案所带来的性能消耗。
在Seata的事务处理中主要有三个重要的角色：事务的协调者（TC）、事务的管理者（TM）和事务的作业管理器（RM）。
- **事务协调者（TC）**主要负责管理全局的分支事务的状态，用于全局性事务的提交和回滚。它会对所有的分支事务进行注册，然后根据各个分支事务的状态来决定是否提交或者回滚全局事务。
- **事务管理者（TM）**用于开启、提交或回滚事务。它会根据业务逻辑来决定何时开启一个新的事务，并在适当的时候提交或回滚该事务。
- **资源管理器（RM）**用于分支事务上的资源管理，向TC注册分支事务，上报分支事务的状态，接收TC的命令来提交或者回滚分支事务。
**回答：**
Seata是一个分布式事务解决方案，主要用来解决微服务架构下跨服务调用时的事务一致性问题。在微服务里，一个业务可能涉及多个服务的数据库操作，传统的本地事务管不了跨服务的情况，容易出现数据不一致，Seata就是干这个的。
它有三个核心角色：TC是事务协调器，负责全局事务的管理；TM是事务发起者，决定事务开始和结束；RM是资源管理器，管理每个服务的本地资源，跟TC通信来执行事务操作。
最常用的是AT模式，这种模式对业务代码侵入性很低，开发的时候基本不用改原来的逻辑。它会通过代理数据源，在本地事务执行时记录数据的前后镜像，提交时如果所有分支都成功，就正常提交；要是有分支失败，TC会通知RM根据镜像回滚数据，这样就能保证多个服务的操作要么都成功，要么都失败。
总的来说，Seata简化了分布式事务的实现，让开发不用太操心跨服务的数据一致性问题，性能也还行，适合大多数微服务场景。
### Seata支持哪些模式的分布式事务？
**分析：**
Seata以下几种模式的分布式事务：
1. AT（Atomikos）模式：AT模式是Seata默认支持的模式，也是最常用的模式之一。在AT模式下，Seata通过在业务代码中嵌入事务上下文，实现对分布式事务的管理。Seata会拦截并解析业务代码中的SQL语句，通过对数据库连接进行拦截和代理，实现事务的管理和协调。
1. TCC（Try-Confirm-Cancel）模式：TCC模式是一种基于补偿机制的分布式事务模式。在TCC模式中，业务逻辑需要实现Try、Confirm和Cancel三个阶段的操作。Seata通过调用业务代码中的Try、Confirm和Cancel方法，并在每个阶段记录相关的操作日志，来实现分布式事务的一致性。
1. SAGA模式：SAGA模式是一种基于事件驱动的分布式事务模式。在SAGA模式中，每个服务都可以发布和订阅事件，通过事件的传递和处理来实现分布式事务的一致性。Seata提供了与SAGA模式兼容的Saga框架，用于管理和协调分布式事务的各个阶段。
1. XA模式：XA模式是一种基于两阶段提交（Two-Phase Commit）协议的分布式事务模式。在XA模式中，Seata通过与数据库的XA事务协议进行交互，实现对分布式事务的管理和协调。XA模式需要数据库本身支持XA事务，并且需要在应用程序中配置相应的XA数据源。
**回答：**
Seata支持三种主要的分布式事务模式。第一种是AT模式，它是自动补偿类型的，基于两阶段提交，用户不用手动写补偿逻辑，Seata会自动生成undo log来实现回滚，适合大部分常规业务场景，用起来简单方便。第二种是TCC模式，需要业务代码里自己实现Try、Confirm、Cancel三个方法，侵入性比较高，但灵活性强，能应对复杂的业务逻辑。第三种是Saga模式，主要用于长事务场景，通过状态机管理流程，每个步骤都有对应的补偿操作，补偿逻辑需要用户自己写，支持异步执行，适合业务流程长、分支多的情况。这三种模式覆盖了不同的业务需求，实际使用时可以根据具体场景选择合适的模式。
### 了解Seata的实现原理吗？
**分析：**
Seata的实现原理主要包括三个核心组件：事务协调器（Transaction Coordinator）、事务管理器（Transaction Manager）和资源管理器（Resource Manager）。
- **事务协调器（Transaction Coordinator）**：事务协调器负责协调和管理分布式事务的整个过程。它接收事务的开始和结束请求，并根据事务的状态进行协调和处理。事务协调器还负责记录和管理事务的全局事务 ID（Global Transaction ID）和分支事务 ID（Branch Transaction ID）。
- **事务管理器（Transaction Manager）**：事务管理器负责全局事务的管理和控制。它协调各个分支事务的提交或回滚，并保证分布式事务的一致性和隔离性。事务管理器还负责与事务协调器进行通信，并将事务的状态变更进行持久化。
- **资源管理器（Resource Manager）**：资源管理器负责管理和控制各个参与者（Participant）的事务操作。它与事务管理器进行通信，并根据事务管理器的指令执行相应的事务操作，包括提交和回滚。
Seata的实现原理基于**两阶段提交（Two-Phase Commit）协议**，具体的机制如下：
1. 一阶段：在事务提交的过程中，首先进行预提交阶段。事务协调器向各个资源管理器发送预提交请求，资源管理器执行相应的事务操作并返回执行结果。在此阶段，业务数据和回滚日志记录在同一个本地事务中提交，并释放本地锁和连接资源。
2. 二阶段：在预提交阶段成功后，进入真正的提交阶段。此阶段主要包括提交异步化和回滚反向补偿两个步骤：
   - 提交异步化：事务协调器发出真正的提交请求，各个资源管理器执行最终的提交操作。这个阶段的操作是非常快速的，以确保事务的提交效率。
   - 回滚反向补偿：如果在预提交阶段中有任何一个资源管理器返回失败结果，事务协调器发出回滚请求，各个资源管理器执行回滚操作，利用一阶段的回滚日志进行反向补偿。
**回答：**
Seata是解决分布式事务的框架，核心有三个角色：TC事务协调者、TM事务管理器、RM资源管理器。TM是发起全局事务的一方，比如微服务里的调用方，它会向TC注册全局事务，生成一个全局唯一的XID。RM是每个微服务里的资源管理者，负责管理分支事务，像数据库操作这些。
具体流程的话，比如用AT模式，TM先跟TC说要开始全局事务，拿到XID。然后调用各个微服务时，XID会在服务间传递。每个微服务里的RM执行本地SQL，执行前会记录数据的前镜像，执行后记录后镜像，同时生成undo log存在数据库里，接着向TC注册分支事务。等所有分支事务都执行完，TM会告诉TC结果。如果都成功，TM通知TC提交全局事务，TC再让各个RM提交分支事务，提交完就把undo log删掉；要是有分支失败，TC就通知RM回滚，RM用undo log把数据恢复到执行前的状态，这样就能保证分布式场景下数据一致了。
### Seata的事务执行流程是什么样的？
**分析：**
Seata事务的执行流程可以简要概括为以下几个步骤：
1. 事务发起方（Transaction Starter）发起全局事务：事务发起方是指发起分布式事务的应用程序或服务。它向Seata的事务协调器发送全局事务的开始请求，生成全局事务ID（Global Transaction ID）。
2. 事务协调器创建全局事务记录：事务协调器接收到全局事务的开始请求后，会为该事务创建相应的全局事务记录，并生成分支事务ID（Branch Transaction ID）。
3. 分支事务注册：事务发起方将全局事务ID和分支事务ID发送给各个参与者（Participant），即资源管理器。参与者将分支事务ID注册到本地事务管理器，并将事务的执行结果反馈给事务协调器。
4. 执行业务逻辑：在分布式事务的上下文中，各个参与者执行各自的本地事务，即执行业务逻辑和数据库操作。
5. 预提交阶段：事务发起方向事务协调器发送预提交请求，事务协调器将预提交请求发送给各个参与者。
6. 执行本地事务确认：参与者接收到预提交请求后，执行本地事务的确认操作，并将本地事务的执行结果反馈给事务协调器。
7. 全局事务提交或回滚：事务协调器根据参与者反馈的结果进行判断，如果所有参与者的本地事务都执行成功，事务协调器发送真正的提交请求给参与者，参与者执行最终的提交操作；如果有任何一个参与者的本地事务执行失败，事务协调器发送回滚请求给参与者，参与者执行回滚操作。
8. 完成全局事务：事务协调器接收到参与者的提交或回滚结果后，根据结果更新全局事务的状态，并通知事务发起方全局事务的最终结果。
**回答：**
Seata事务执行流程大概是这样的：用户发起一个全局事务时，TM也就是事务管理器会先跟TC事务协调器注册，拿到全局事务ID。接着每个微服务作为RM资源管理器，在执行自己的本地事务前，会先去TC注册分支事务，把自己和全局事务ID关联起来。然后执行本地SQL操作，同时生成回滚日志undo log，之后告诉TC自己这个分支事务的状态。等所有分支事务都跑完了，如果都成功，TM就通知TC提交全局事务，TC再让各个RM提交分支事务，RM删掉undo log就完成了。要是中间有分支事务失败，TM会通知TC回滚，TC就指挥所有RM根据之前的undo log把本地事务回滚回去，恢复到执行前的状态。整个过程就是TM发起和控制，TC负责协调，RM执行具体事务并配合回滚或提交。
### Seata的事务回滚是怎么实现的？
**分析：**
Seata的事务回滚是通过回滚日志实现的。每个参与者在执行本地事务期间生成回滚日志，记录了对数据的修改操作。
当需要回滚事务时，事务协调器向参与者发送回滚请求，参与者根据回滚日志中的信息执行撤销操作，将数据恢复到事务开始前的状态。
回滚日志的管理和存储是Seata的核心机制，可以选择将日志存储在不同的介质中。通过回滚日志的持久化和恢复，Seata确保了事务的一致性和恢复性。
**回答：**
Seata的事务回滚主要靠undo log实现。分布式事务里每个分支事务执行时，Seata的RM会先记录一份undo log，里面存着数据修改前的状态、修改后的状态和主键这些信息。当整个事务需要回滚时，TC会通知各RM执行回滚。这时候RM就根据undo log里的修改前状态生成恢复SQL，把数据改回事务执行前的样子。同时回滚时会检查当前数据是否和undo log里修改后的状态一致，一致才执行回滚，避免并发操作导致数据错乱，这样就能保证回滚正确了。

### 你们的服务怎么做监控和告警？
**分析：**
我们使用Prometheus和Grafana来实现整个微服务集群的监控和告警：
1. Prometheus：Prometheus 是一个开源的监控系统，具有灵活的数据模型和强大的查询语言，能够收集和存储时间序列数据。它可以通过HTTP协议定期拉取微服务的指标数据，并提供可扩展的存储和查询功能。
2. Grafana：Grafana 是一个开源的可视化仪表板工具，可以与 Prometheus 结合使用，创建实时和历史数据的仪表板。Grafana 提供了丰富的图表和可视化选项，可以帮助用户更好地理解和分析微服务的性能和状态。
**回答：**
我们做服务监控主要分几个层面，先看基础设施，比如服务器的CPU内存磁盘使用率，网络流量这些基础指标，得实时盯着别出问题。然后是应用层面，关注接口的响应时间、错误率，还有关键日志里的异常信息，确保服务本身跑的正常。最后是业务层面，比如核心的订单量、支付成功率这些，能直接反映用户体验的指标也得监控。
告警这块，首先得把指标阈值设好，比如CPU超过80%就告警，但不能太死板，有些时段流量高可能得动态调整阈值，避免老发无效告警。然后按严重程度分级，特别紧急的比如支付接口挂了，直接电话或者企业微信电话通知负责人；一般问题就短信或企业微信消息，避免半夜老打扰人。告警发出来后，得能自动关联到对应的服务模块，方便我们快速定位问题，尽快处理。平时也会定期看监控数据，优化阈值和告警策略，尽量少漏报也别瞎报。
### 你们的服务怎么做日志收集？
**分析：**
日志收集有很多种方案，我们用的是ELK：
- **Elasticsearch**：Elasticsearch是一个分布式搜索和分析引擎，用于存储和索引大量的日志数据。它提供了快速的搜索和聚合功能，可以高效地处理大规模的日志数据。
- **Logstash**：Logstash是一个用于收集、过滤和转发日志数据的工具。它可以从各种来源（如文件、网络、消息队列等）收集日志数据，并对数据进行处理和转换，然后将其发送到Elasticsearch进行存储和索引。
- **Kibana**：Kibana是一个用于日志数据可视化和分析的工具。它提供了丰富的图表、仪表盘和搜索功能，可以帮助用户实时监控和分析日志数据，发现潜在的问题和趋势。
简单说，这三者里**Elasticsearch**提供数据存储和检索能力，**Logstash**负责将日志收集到ES，**Kibana**负责日志数据的可视化分析。
1. 在每个微服务中配置日志输出：将微服务的日志输出到标准输出（stdout）或日志文件。
2. 使用Logstash收集日志：配置Logstash收集器，通过配置输入插件（如文件输入、网络输入等）监听微服务的日志输出，并进行过滤和处理。
3. 将日志数据发送到Elasticsearch：配置Logstash的输出插件，将经过处理的日志数据发送到Elasticsearch进行存储和索引。
4. 使用Kibana进行可视化和分析：通过Kibana连接到Elasticsearch，创建仪表盘、图表和搜索查询，实时监控和分析微服务的日志数据。
除了应用最广泛的ELK，还有一些其它的方案比如Fluentd、Graylog、Loki、Filebeat，一些云厂商也提供了付费方案，比如阿里云的sls。
**回答：**
我们服务的日志收集主要是从应用输出到后续处理一步步来的。
应用里用log4j、logback这些常用的日志框架，按统一格式打日志，比如时间、日志级别、服务名、请求ID、具体内容都带上，这样后面处理起来方便。日志先写到本地文件，小服务直接存本地也行，量大的话就用Filebeat或者Fluentd这种工具，它们轻量，能实时读本地日志文件，然后转发出去，不占应用本身太多资源。
传输过去的日志存到Elasticsearch里，因为它存量大，查起来也快，配上Kibana就能看日志趋势、搜具体内容，排查问题方便。
另外会设置日志轮转，单个文件到一定大小就切分，避免占满磁盘，线上日志一般保留一周，旧的归档到对象存储。
最后还会监控日志情况，比如错误日志突然变多、日志量异常增长就告警，能及时发现问题。
### **说下你对DDD的理解？**
**分析：**
**领域驱动设计（DDD）是一种软件开发方法**，旨在帮助开发人员更好地理解和设计复杂的软件系统。它的主要目的是让开发人员和领域专家能够更好地协作，以满足业务需求。
**DDD的关键概念包括领域模型和限界上下文。**领域模型描述了业务领域的规则和逻辑，让开发人员更好地理解业务需求；限界上下文则定义了一个特定的业务领域内的模型和代码，使其可以独立于其他上下文进行开发和维护。
此外，**DDD还强调了分层架构和事件溯源的重要性**。分层架构将系统划分为不同层次，各层次有不同的职责和角色，便于开发和维护；事件溯源则是一种存储和处理业务事件的技术，支持审计、合规和业务分析等需求。
总之，DDD是一种设计和开发复杂软件系统的 方法，它通过建立领域模型、分层架构、限界上下文和事件溯源等技术，使得开发人员能够更好地理解和满足业务需求。
**回答：**
我理解DDD就是领域驱动设计，主要用来解决业务比较复杂的系统设计问题。核心思路是从业务领域本身出发，先把实际的业务流程、规则梳理清楚，然后抽象成领域模型，让模型能真实反映业务逻辑，而不是一开始就想着技术怎么实现。接着会拆分限界上下文，把大系统分成一个个独立的业务模块，每个模块有自己的领域模型，这样模块之间耦合低，也不会因为业务交叉导致混乱。还有聚合根，就是每个模块里管理领域对象的核心，保证数据操作的时候是一致的。总的来说，DDD能让业务和技术结合得更紧密，代码逻辑跟着业务走，后期维护起来也方便，特别是业务复杂的时候，用DDD能让系统结构更清晰，不容易乱。
