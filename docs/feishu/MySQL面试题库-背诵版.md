# MySQL 面试题库 · 背诵版
> 来源：[MySQL 面试题库](https://ls8sck0zrg.feishu.cn/wiki/wikcnGHC6ySX9qYhlCvEXKWvMyb)，结合小林coding、JavaGuide 等资料整理为标准背诵答案
# 一、SQL 语法
## 1. count(主键) 和 count(非主键) 结果会不同吗？
**背诵**：会不同。count(列) 统计该列非 NULL 值的数量。主键不能为 NULL，所以 count(主键) = 全表行数；非主键列可能有 NULL，count(非主键) 只统计非 NULL 的行数。
## 2. 内连接、外连接有什么区别？
**背诵**：内连接（INNER JOIN）只返回两表匹配的行；外连接返回匹配 + 不匹配的行，分左连接（LEFT JOIN，左表全保留，右表无匹配补 NULL）和右连接（RIGHT JOIN，反之）。
## 3. 外连接时 on 和 where 过滤条件区别？
**背诵**：内连接中 on 和 where 等效。外连接中：on 是连接条件，在连接时过滤（不影响左表/右表全量保留的特性）；where 是连接完成后对结果集再筛选，会把补 NULL 的行也过滤掉。
## 4. having 与 where 的区别？
**背诵**：where 在 GROUP BY 分组之前过滤行，不能用聚合函数；having 在分组之后过滤，可以使用聚合函数。
## 5. EXISTS 和 IN 的区别？
**背诵**：IN 先执行子查询生成结果集，再逐条匹配外表；EXISTS 对外表每行执行一次子查询，查到即返回 true。小表驱动大表用 IN，大表驱动小表用 EXISTS。EXISTS 只要找到一条就停止，子查询结果大时性能更好。另外 NOT IN 遇到 NULL 会结果异常，NOT EXISTS 不会。
## 6. MySQL 的约束有哪些？
**背诵**：主键约束（PRIMARY KEY，唯一且非空）、唯一约束（UNIQUE）、非空约束（NOT NULL）、默认约束（DEFAULT）、外键约束（FOREIGN KEY）、检查约束（CHECK，MySQL 8.0.16+ 才真正生效）、自增（AUTO_INCREMENT）。
## 7. delete、drop、truncate 有什么区别？
**背诵**：delete 是 DML，逐行删除、可带 where、可回滚、记录 undo/redo 日志、不重置自增；truncate 是 DDL，整表清空、不可回滚、重置自增、速度快；drop 是 DDL，连表结构一起删除。速度：drop > truncate > delete。
## 8. union 和 union all 的区别？
**背诵**：union 会对结果集去重并排序，性能低；union all 直接合并不去重，性能高。确定无重复数据时优先用 union all。
## 9. 数据库三大范式？解决什么问题？缺点？
**背诵**：1NF 字段原子不可再分；2NF 在 1NF 基础上消除非主键字段对主键的部分依赖（每张表只描述一件事）；3NF 在 2NF 基础上消除传递依赖（非主键字段不依赖其他非主键字段）。范式解决数据冗余、更新异常、插入异常、删除异常。缺点：表拆得越多 join 越多，查询性能下降，所以实际开发会适当反范式（冗余字段换查询性能）。
## 10. count(*) 性能比 count(1) 好吗？
**背诵**：一样好。InnoDB 中 count(*)、count(1)、count(主键) 性能基本相同，MySQL 对 count(*) 做了专门优化（会选择最小的索引树扫描）。count(普通字段) 最慢，因为要判断 NULL。MyISAM 的 count(*) 是 O(1)（存了行数），InnoDB 需要扫描。
# 二、存储引擎
## 11. 一条查询 SQL 的执行全过程？
**背诵**：客户端 → 连接器（建立连接、权限校验）→ 查询缓存（8.0 已删除）→ 分析器（词法语法解析）→ 优化器（选择索引、生成执行计划）→ 执行器（调用存储引擎接口）→ InnoDB 引擎（Buffer Pool 查数据页，不在则读磁盘）→ 返回结果。
**图解**：
```
客户端
  │
  ▼
┌─────────────── MySQL Server 层 ───────────────┐
│ 连接器（连接管理、权限验证）                      │
│   ▼                                            │
│ 分析器（词法分析、语法分析 → 语法树）              │
│   ▼                                            │
│ 优化器（索引选择、执行计划）                      │
│   ▼                                            │
│ 执行器（判断权限、调用引擎接口）                   │
└───────────────┬────────────────────────────────┘
                ▼
┌──────────── InnoDB 存储引擎层 ────────────┐
│ Buffer Pool ──命中──→ 直接返回数据页         │
│     │ 未命中                                │
│     ▼                                      │
│   磁盘读取数据页 → 加载到 Buffer Pool → 返回  │
└─────────────────────────────────────────────┘
```
## 12. MySQL 存储引擎有哪些？
**背诵**：InnoDB（默认，支持事务、行锁、外键、MVCC）、MyISAM（不支持事务、表锁、查询快）、Memory（内存存储，重启丢数据）、Archive（归档，只支持插入和查询）等。
## 13. MyISAM 和 InnoDB 有什么区别？
**背诵**：① 事务：InnoDB 支持 ACID，MyISAM 不支持；② 锁：InnoDB 行锁+间隙锁，MyISAM 只有表锁；③ 索引：InnoDB 聚簇索引（索引和数据在一起），MyISAM 非聚簇（索引和数据分离）；④ 崩溃恢复：InnoDB 有 redo log 可恢复，MyISAM 易损坏；⑤ 外键：InnoDB 支持，MyISAM 不支持；⑥ count：MyISAM 存了总行数 O(1)，InnoDB 要扫描。
## 14. 为什么 InnoDB 是默认引擎？
**背诵**：因为 InnoDB 支持事务、行级锁（高并发）、MVCC、外键、崩溃恢复，满足互联网业务对一致性和并发的要求；MyISAM 只适合读多写少的场景。
## 15. count(*) 哪个存储引擎更快？
**背诵**：MyISAM 快，它把表的总行数存在磁盘上，count(*) 直接返回 O(1)；InnoDB 由于 MVCC 不同事务看到的行数不同，需要实时扫描，O(n)。
## 16. NULL 值是如何存储的？
**背诵**：InnoDB 行格式中用「NULL 值列表」按位（bit）标记哪些列为 NULL，每个可为 NULL 的列占 1 bit，不占实际数据空间。所以 NULL 列本身几乎不占存储空间，但索引处理 NULL 有额外开销。
## 17. char 和 varchar 区别？哪个性能好？
**背诵**：char 定长，不足补空格，存取快但浪费空间，适合长度固定的字段（如手机号、MD5）；varchar 变长，额外 1~2 字节存长度，节省空间。char 性能略好（无需计算长度、更新不会导致行迁移），但绝大多数场景用 varchar。
## 18. varchar(10) 实际只存 6 字节，内存和磁盘各占多少？
**背诵**：varchar 按实际长度存储：磁盘占 6 字节数据 + 1~2 字节长度前缀；内存（Buffer Pool）中也是按实际长度存放。char(10) 才会固定占 10 字节。
## 19. 内存特别大，MySQL 缓存能替代 Redis 吗？
**背诵**：不能。① MySQL Buffer Pool 只缓存数据页，不支持丰富的数据结构（List/Set/ZSet）；② 没有过期策略、LRU 淘汰不可控；③ 不支持分布式、集群；④ 没有发布订阅、Lua 脚本等功能；⑤ MySQL 缓存是为了减少磁盘 IO，Redis 是为应用层提供高速 KV 服务，定位不同。
# 三、索引结构（重要）
## 20. MySQL 有哪些索引类型？
**背诵**：按数据结构分：B+树索引、Hash 索引、全文索引（Full-text）、空间索引（R-Tree）。按物理存储分：聚簇索引、非聚簇索引（二级索引）。按字段特性分：主键索引、唯一索引、普通索引、前缀索引。按字段个数分：单列索引、联合索引。
## 21. InnoDB 的索引数据结构是什么？
**背诵**：B+ 树。非叶子节点只存索引键值和指针，叶子节点存数据（聚簇索引存整行，二级索引存主键值），叶子节点之间用双向链表连接。
**图解**（3 层 B+ 树）：
```
                ┌──────────────┐
                │  根节点(页)    │        非叶子节点：只存键值+指针
                │  [10 | 20]   │        不存数据
                └──┬─────┬──┬──┘
                   │     │  │
        ┌──────────┘     │  └──────────┐
        ▼                ▼             ▼
   ┌─────────┐     ┌─────────┐    ┌─────────┐
   │ [<10]   │     │ [10|20) │    │ [>=20]  │     非叶子节点
   │ [3|5|7] │     │[12|15|18│    │[22|25|30│
   └──┬──────┘     └──┬──────┘    └──┬──────┘
      ▼               ▼              ▼
 ┌────────┐     ┌────────┐      ┌────────┐
 │3,5,7   │ ←→  │12,15,18│ ←→  │22,25,30│     叶子节点：存完整数据
 │+行数据 │     │+行数据 │      │+行数据 │     双向链表连接 → 范围查询高效
 └────────┘     └────────┘      └────────┘
```
## 22. B+ 树的特性？
**背诵**：① 多叉平衡树，所有叶子节点在同一层；② 非叶子节点只存键值不存数据；③ 叶子节点存全部数据，且按顺序双向链表连接；④ 查询都要从根到叶子，IO 次数稳定；⑤ 树高低（3~4 层可存千万级数据）。
## 23. B+ 树和 B 树的区别？
**背诵**：① B 树所有节点都存数据，B+ 树只有叶子节点存数据；② B+ 树非叶子节点只存键值，单节点能存更多键，树更矮、IO 更少；③ B+ 树叶子节点有双向链表，范围查询和排序高效；④ B 树查到即停（可能在非叶子节点），B+ 树必须到叶子，查询性能稳定。
## 24. MySQL 为什么用 B+ 树？
**背诵**：① 矮胖树，3~4 层存千万数据，磁盘 IO 次数少；② 非叶子节点只存键值，单页（16KB）能放更多索引项；③ 叶子节点双向链表，天然支持范围查询和排序；④ 查询路径固定，性能稳定可预测。
## 25. 为什么用 B+ 树而不用红黑树？
**背诵**：红黑树是二叉树，数据量大时树高很深（千万级约 24 层），每层一次磁盘 IO 不可接受；B+ 树一个节点存几百上千个键，3~4 层就够。且红黑树是内存数据结构，不适合磁盘场景。
## 26. 为什么用 B+ 树而不用 B 树？
**背诵**：① B 树非叶子节点也存数据，单节点能存的键少，树更高 IO 更多；② B+ 树叶子节点链表连接，范围查询只需遍历叶子，B 树范围查询要中序遍历整棵树；③ B+ 树查询都要到叶子，性能稳定。
## 27. 为什么用 B+ 树而不用哈希表？
**背诵**：哈希等值查询 O(1) 更快，但：① 不支持范围查询（哈希后无序）；② 不支持排序；③ 不支持模糊查询和最左前缀匹配；④ 哈希碰撞时性能退化；⑤ 无法利用索引完成覆盖查询。数据库业务大量范围查询，所以选 B+ 树。（InnoDB 有自适应哈希索引作为内部优化）
## 28. B+ 树的优点和缺点？
**背诵**：优点：树矮 IO 少、范围查询高效、查询稳定、支持排序。缺点：① 写入时可能引起节点分裂，有维护成本；② 非顺序插入（如 UUID 主键）导致频繁分裂和页碎片；③ 索引占额外磁盘空间。
## 29. 聚簇索引和非聚簇索引的区别？
**背诵**：聚簇索引：索引和数据存在一起，B+ 树叶子节点存整行数据，一张表只有一个（通常是主键）。非聚簇索引（二级索引）：索引和数据分开，叶子节点存主键值，可以有多个，查完可能要回表。
**图解**：
```
聚簇索引（主键 id）              非聚簇索引（name）
    B+ 树                          B+ 树
  ┌──[5|10]──┐                  ┌──[张|李]──┐
  ▼    ▼    ▼                  ▼    ▼    ▼
[id=3] [id=7]...            [name=王] [name=赵]...
 叶子存整行数据               叶子只存主键值 id=5
 (id,name,age,...)                 │
                                   ▼ 回表
                            再去聚簇索引按 id=5 查整行
```
## 30. 什么是覆盖索引？
**背诵**：查询所需的字段全部包含在二级索引中（索引键 + 主键值），无需回表直接返回，这个索引就叫覆盖索引。是最优的索引优化手段，EXPLAIN 中 Extra 显示 Using index。
## 31. 什么情况下会回表？
**背诵**：使用二级索引查询，且查询的字段不完全在二级索引中时：先在二级索引 B+ 树找到主键值，再拿主键值去聚簇索引查整行数据，这个二次查询过程就是回表。避免方式：覆盖索引。
**图解**（`SELECT * FROM user WHERE name='张三'`，name 有二级索引）：
```
① 二级索引树(name)          ② 聚簇索引树(id)
  name=张三                   id=5
    │                          │
    ▼ 找到主键                 ▼ 按主键查
  叶子节点: (张三, id=5) ──────→ 叶子节点: 整行数据
                                 (id=5, name=张三, age=20, ...)
查了两棵 B+ 树 = 回表；如果 SELECT 只要 name 和 id，第②步不用走 = 覆盖索引
```
## 32. insert 操作对 B+ 树的改变？
**背诵**：按键值找到目标叶子页插入；页满则分裂成两个页，中间键上浮到父节点；父节点满则继续向上分裂，可能增加树高。自增主键顺序插入只在最右页追加，几乎不分裂；无序主键（UUID）随机插入，分裂频繁、产生碎片。
## 33. 两千万数据的表，B+ 树高度是多少？
**背诵**：一般 3 层。估算：一页 16KB，非叶子节点一个索引项（键+指针）约 16 字节，一页约存 1000 个指针；叶子节点一行数据按 1KB 算，一页存 16 行。两层：1000×16=1.6 万行；三层：1000×1000×16=1600 万行；四层可达百亿。所以两千万数据约 3~4 层。
# 四、索引应用（重要）
## 34. MySQL 有哪些索引？
**背诵**：主键索引（唯一且非空，一表一个）、唯一索引（唯一，可 NULL，可多个）、普通索引、前缀索引（取字段前 N 个字符）、联合索引（多列组合）、全文索引。
## 35. 主键是聚簇索引吗？
**背诵**：在 InnoDB 中是的。主键索引的 B+ 树叶子节点直接存整行数据。如果没设主键，InnoDB 会选第一个非空唯一索引代替；都没有则生成隐藏的 row_id 作为聚簇索引。
## 36. 主键为什么不推荐有业务含义？
**背诵**：① 业务可能变化，主键一旦使用不便修改；② 业务主键可能无序（如手机号），导致插入时页分裂；③ 业务字段可能较长，所有二级索引都会存主键值，主键越大二级索引越占空间。
## 37. 主键用自增还是 UUID？
**背诵**：推荐自增。① 自增有序，插入时只在 B+ 树最右追加，不分裂；UUID 无序，随机插入导致频繁页分裂和碎片；② 自增 int/bigint 占 4/8 字节，UUID 字符串占 36 字符，主键越大所有二级索引越大；③ 自增范围查询效率高。分布式场景需要全局唯一可用雪花算法（趋势递增）。
## 38. 普通索引和唯一索引的区别？哪个更新性能好？
**背诵**：查询性能几乎无差别（普通索引查到后多扫一条确认）。更新性能普通索引更好：普通索引更新可直接写 change buffer，下次读时合并；唯一索引因为要检查唯一性约束，必须先把数据页读入内存，无法使用 change buffer。
## 39. 主键怎么设置？不设置会怎样？
**背诵**：建表时指定 PRIMARY KEY，推荐自增 bigint 无业务含义字段。不设置时 InnoDB 会选第一个非空唯一索引作为聚簇索引；都没有则自动生成 6 字节隐藏 row_id，浪费空间且不可控。
## 40. 什么是外键约束？
**背诵**：外键（FOREIGN KEY）保证两张表数据的参照完整性：子表的外键值必须在主表主键中存在。可设置级联操作（ON DELETE CASCADE / SET NULL / RESTRICT）。
## 41. 外键的优劣势？
**背诵**：优势：数据库层面保证数据一致性、防止脏数据。劣势：① 每次增删改都要检查约束，影响性能；② 高并发下外键检查产生额外锁，易死锁；③ 分库分表后外键无法跨库；④ 互联网高并发场景一般不用外键，改在应用层保证一致性。
## 42. 为什么要建索引？
**背诵**：快速定位数据，避免全表扫描，把查询从 O(n) 降到 O(log n)。还能加速排序（order by）、分组（group by）、连接（join）。
## 43. 一般选择什么字段建索引？
**背诵**：① where 高频查询条件；② order by / group by 字段；③ join 关联字段（外键）；④ 区分度高（选择性高）的字段；⑤ 覆盖查询字段的联合索引。不选：区分度低的字段（如性别）、频繁更新的字段、大文本字段。
## 44. 索引越多越好吗？
**背诵**：不是。① 每个索引都是一棵 B+ 树，占磁盘空间；② 增删改要维护所有索引树，写入变慢；③ 优化器选择索引的时间变长，可能选错。一般单表索引不超过 5~6 个。
## 45. 什么时候不用索引更好？
**背诵**：① 表数据量很小（全表扫描比走索引还快）；② 查询要返回表中大部分数据（回表成本高于全表扫描）；③ 区分度极低的字段；④ 频繁更新、很少查询的字段。
## 46. 字段为什么要定义为 NOT NULL？
**背诵**：① NULL 值使索引统计和比较更复杂，优化器处理 NULL 有额外开销；② NULL 参与运算结果都是 NULL，易出 bug；③ count(列) 不统计 NULL，结果可能不符合预期；④ NULL 列需要额外位标记存储；⑤ 可用默认值（0、空串）代替 NULL。
## 47. 索引怎么优化？
**背诵**：① 覆盖索引避免回表；② 联合索引遵循最左前缀，高频等值列放左边；③ 索引下推减少回表次数；④ 长字符串用前缀索引；⑤ 避免索引失效（不在索引列用函数/运算/隐式转换、不以 % 开头 like）；⑥ 定期 ANALYZE TABLE 更新统计信息；⑦ 用 EXPLAIN 分析执行计划。
## 48. 建立了索引，查询一定会用到吗？
**背诵**：不一定。优化器基于成本估算选择执行计划，以下情况可能不走索引：① 表中数据太少；② 查询返回数据占比太大（回表成本高）；③ 索引列上使用函数、运算、隐式类型转换；④ like 以 % 开头；⑤ 不满足最左前缀；⑥ 统计信息过期导致优化器误判。
## 49. varchar 日期字段有索引，where time=20230922 不加引号会命中索引吗？
**背诵**：不会命中（或说可能失效）。字段是 varchar、值是数字，会发生隐式类型转换——相当于对索引列使用了函数（CAST），导致索引失效。规则：字符串与数字比较时，MySQL 把字符串转成数字。所以查询条件类型要和字段类型一致。
## 50. MySQL 新版本解决了哪些索引失效的情况？
**背诵**：MySQL 8.0 的改进：① 函数索引/表达式索引（可对函数结果建索引）；② 降序索引（解决 order by 混排 filesort）；③ 不可见索引（invisible index，可灰度测试删索引）；④ 直方图统计（优化器估算更准）；⑤ 索引跳跃扫描（Index Skip Scan，联合索引跳过前导列也可能用索引）。
## 51. 什么是最左匹配原则？
**背诵**：联合索引 (a,b,c) 按从左到右顺序构建 B+ 树，先按 a 排序，a 相同再按 b 排序。查询必须从最左列开始连续匹配才能用上索引，跳过 a 直接查 b 则索引失效（因为 b 在全局无序）。(a,b,c) 相当于建了 (a)、(a,b)、(a,b,c) 三个索引。
## 52. 建立联合索引有什么注意点？
**背诵**：① 高频等值查询字段放左边，范围查询字段放右边（范围右边的列用不上索引）；② 把区分度高的列放前面；③ 考虑覆盖索引，把 select 的列包含进来避免回表；④ 列数不宜过多（3 列以内），索引维护成本高；⑤ 已有 (a,b) 就不必再建 (a)。
## 53. 什么是索引下推？什么时候下推？
**背诵**：索引下推（ICP，Index Condition Pushdown，MySQL 5.6+）：把 where 中索引列的过滤条件下推到存储引擎层，在遍历索引时就过滤掉不满足的记录，减少回表次数。例：联合索引 (name, age)，查询 `where name like '张%' and age = 20`，无 ICP 时按 name 回表后再过滤 age；有 ICP 时在索引中直接过滤 age 再回表。
## 54. 联合索引 (a,b,c)，各种查询走索引情况？
**背诵**：`where a=1` 走 a；`where a=1 and b=2` 走 a,b；`where a=1 and b=2 and c=3` 全走；`where b=2` 不走（跳过 a）；`where a=1 and c=3` 只走 a（b 断档，c 用不上索引，但 c 可用于索引下推过滤）；`where a>1 and b=2` 走 a，b 用不上（a 是范围，b 无序）；`where a=1 and b>2 and c=3` 走 a,b，c 用不上。
## 55. where a>1 and b=2 and c<3 怎么建索引？
**背诵**：等值列放前，范围列放后：(b, a, c) 或 (b, c, a)。b 是等值放最左；a、c 都是范围，哪个区分度高放前面。注意 a 或 c 排第二时，第三列用不上索引排序但可用于过滤（索引下推）。
## 56. where a=? and b=? order by c 怎么建索引？
**背诵**：(a, b, c)。a、b 等值查询，c 在索引中有序，order by c 直接利用索引顺序，避免 filesort。
## 57. where a>100 and b=100 and c=123 order by d 怎么建索引？
**背诵**：(b, c, a, d)。等值列 b、c 放最前，范围列 a 放其后，d 放最后。因为 a 是范围查询，其后的 d 在索引中无序，order by d 仍需 filesort；若想避免 filesort，需业务上把 a 的条件改成等值或去掉排序需求。
## 58. select b from table where a=10 and c>20 怎么建索引？
**背诵**：(a, c, b)。a 等值、c 范围，b 放最后做覆盖索引避免回表（select 只有 b）。
## 59. select id,name from XX where age>10 and name like 'xx%'，联合索引 (name,age)，说查询过程？
**背诵**：name like 'xx%' 前缀匹配可走索引范围扫描，定位到 name 以 xx 开头的索引区间；age>10 条件通过索引下推在索引上过滤（age 在联合索引中）；select 的 id（主键，二级索引叶子自带）和 name 都在索引中 → 覆盖索引，无需回表，直接返回。
## 60. where id NOT IN (?, ?, ?) 会走索引吗？
**背诵**：id 是主键时，NOT IN 少量值可能走索引范围扫描（把区间拆成几段）；但 NOT IN 的值占比大时优化器认为全表扫描更划算，不走索引。另外 NOT IN 子查询含 NULL 会导致结果为空（NOT IN 遇 NULL 返回 UNKNOWN），建议用 NOT EXISTS 替代。
## 61. 查询条件包含索引列和非索引列，查询流程？
**背诵**：先用索引列在二级索引 B+ 树定位到匹配的主键集合（若有索引下推则先在索引上过滤能过滤的条件）→ 拿主键回表查聚簇索引取整行 → 在 server 层用非索引列条件过滤 → 返回结果。
# 五、事务（重要）
## 62. 事务有什么特性（ACID）？
**背诵**：原子性（Atomicity）：要么全做要么全不做，由 undo log 保证；一致性（Consistency）：事务前后数据满足完整性约束，是最终目标，由其他三个特性共同保证；隔离性（Isolation）：并发事务互不干扰，由 MVCC + 锁保证；持久性（Durability）：提交后永久生效，由 redo log 保证。
## 63. 事务的隔离性如何保证？
**背诵**：读操作靠 MVCC（Read View + undo log 版本链）实现快照读，读写不互斥；写操作靠锁（行锁、间隙锁、临键锁）保证。串行化级别则所有操作都加锁。
## 64. 事务的持久性如何保证？
**背诵**：redo log（重做日志）。修改先写 redo log（WAL 预写日志）并刷盘，再异步把数据页刷盘。崩溃恢复时用 redo log 重放已提交事务的修改。
## 65. 事务的原子性如何保证？
**背诵**：undo log（回滚日志）。每次修改前记录旧值，事务回滚时用 undo log 恢复到修改前的状态。
## 66. MySQL 事务和 Redis 事务的区别？
**背诵**：① MySQL 事务支持回滚（undo log），Redis 事务不支持回滚（命令执行失败不影响其他命令）；② MySQL 有 ACID 完整保证，Redis 事务只是把命令打包顺序执行（MULTI/EXEC），保证原子性执行但不保证一致性；③ Redis 事务没有隔离级别概念，执行期间不会被其他客户端命令插入（单线程）；④ Redis 用 WATCH 实现乐观锁。
## 67. 事务隔离级别有哪些？分别解决什么问题？
**背诵**：读未提交（RU）：啥问题都没解决，可能脏读、不可重复读、幻读；读已提交（RC）：解决脏读；可重复读（RR，InnoDB 默认）：解决脏读、不可重复读，并通过 MVCC+临键锁很大程度解决幻读；串行化：全部解决，但性能最差。脏读=读到别人未提交的数据；不可重复读=同一行前后两次读结果不同；幻读=前后两次查询行数不同。
## 68. 串行化隔离级别怎么实现的？
**背诵**：所有读操作也加共享锁（普通 SELECT 转为 SELECT ... LOCK IN SHARE MODE），读写、写读、写写全部互斥，事务串行执行。
## 69. 脏读和幻读的区别？
**背诵**：脏读是读到了其他事务「未提交」的数据；幻读是同一事务内两次相同查询返回的「行数」不同（读到了其他事务已提交的新增数据）。脏读针对未提交数据，幻读针对新增/删除的行数变化；不可重复读针对同一行内容的修改。
## 70. MySQL 默认隔离级别？怎么实现的？
**背诵**：可重复读（RR）。通过 MVCC 实现：事务启动时（第一次快照读时）创建 Read View，整个事务期间复用同一个 Read View，所以多次读取结果一致。当前读（for update、update、delete）配合临键锁防幻读。
## 71. 介绍一下 MVCC？
**背诵**：MVCC（多版本并发控制）：每行记录有两个隐藏列——trx_id（最近修改的事务 id）和 roll_pointer（指向 undo log 中旧版本的指针），形成版本链。事务读取时创建 Read View（包含当前活跃事务 id 列表 m_ids、最小活跃事务 id min_trx_id、下一个事务 id max_trx_id、创建者事务 id），通过版本链上 trx_id 与 Read View 比对判断哪个版本可见，实现无锁的快照读，读写不互斥。
**图解**（版本链 + Read View）：
```
行记录的版本链（undo log）：
  当前版本          旧版本           更旧版本
┌──────────┐    ┌──────────┐    ┌──────────┐
│ trx_id=52│───→│ trx_id=51│───→│ trx_id=50│
│ 余额=200 │    │ 余额=150 │    │ 余额=100 │
└──────────┘    └──────────┘    └──────────┘
   未提交          未提交           已提交

Read View（事务启动时拍照）：
┌─────────────────────────────────┐
│ m_ids = [51, 52]  活跃事务列表    │
│ min_trx_id = 51   最小活跃 id    │
│ max_trx_id = 53   下一个事务 id  │
│ creator_trx_id = 53 本事务 id    │
└─────────────────────────────────┘
判断：trx_id=52 在 m_ids 中 → 不可见；trx_id=51 在 m_ids 中 → 不可见；
     trx_id=50 < min_trx_id → 可见 ✓（读到余额 100）
```
## 72. MVCC 如何判断行记录对某事务是否可见？
**背诵**：对版本链中每个版本的 trx_id 判断：① trx_id < min_trx_id（修改事务在 Read View 创建前已提交）→ 可见；② trx_id >= max_trx_id（修改事务在 Read View 创建后才开启）→ 不可见；③ min_trx_id <= trx_id < max_trx_id：若 trx_id 在 m_ids（活跃列表）中 → 不可见（未提交），不在 → 可见（已提交）；④ trx_id = 自己的事务 id → 可见。不可见则沿 roll_pointer 找下一个版本。
## 73. RC 和 RR 实现 MVCC 的区别？
**背诵**：Read View 创建时机不同。RC：每条 SELECT 语句执行前都重新生成 Read View，所以能读到别的事务刚提交的数据（不可重复读）；RR：事务第一次快照读时生成 Read View，整个事务复用，所以多次读结果一致。
## 74. 为什么互联网公司用读已提交（RC）？
**背诵**：① RC 下间隙锁基本不生效（只锁行），锁冲突和死锁概率小，并发度高；② RC 的 Read View 用完即弃，undo log 版本链可以及时清理，不会膨胀；③ 配合 binlog row 格式，RC 主从复制不会丢数据（statement 格式在 RC 下才有主从不一致问题）。MySQL 默认 RR 是历史原因（早期 statement 格式 binlog 在 RC 下有 bug）。
## 75. RR 如何解决不可重复读？
**背诵**：事务第一次快照读时生成 Read View 并全程复用，其他事务即使修改并提交了数据，该事务读到的仍是事务启动时的快照版本。
## 76. RR 如何解决幻读？
**背诵**：分两种读：快照读（普通 SELECT）靠 MVCC 的 Read View，看不到事务启动后新增的行，解决幻读；当前读（SELECT ... FOR UPDATE、UPDATE、DELETE）靠临键锁（Next-Key Lock = 行锁 + 间隙锁）锁住索引区间，阻止其他事务在区间内插入新行。
## 77. RR 完全解决幻读了吗？
**背诵**：没有完全解决。快照读无幻读（MVCC），当前读靠临键锁防幻读，但存在边界场景：① 事务先快照读，另一事务插入新行并提交，本事务再对相同范围做当前读（或 update 了新插入的行后再快照读），会看到新行——幻读出现；② 根本原因是当前读读最新版本，且更新会修改记录的 trx_id 为本事务，导致该记录对本事务可见。
## 78. RR 什么时候会出现幻读？
**背诵**：典型场景：事务 A 开启后快照读（看不到新数据）→ 事务 B 插入一行并提交 → 事务 A 执行 UPDATE 覆盖了 B 插入的行（当前读，会更新该行 trx_id 为 A）→ 事务 A 再次快照读，这行对 A 可见了 → 幻读。避免方式：事务开启后第一时间用 SELECT ... FOR UPDATE 加锁，把快照读升级为当前读。
## 79. RR 的 MVCC 完全解决不可重复读了吗？
**背诵**：对快照读完全解决了（同一个 Read View）。但如果事务内执行了当前读（UPDATE/DELETE/FOR UPDATE），读到的是最新已提交数据，之后再快照读会看到本事务的修改，前后结果可能不同——但这属于自己修改自己可见，符合语义。
## 80. 一个事务里有特别多 SQL 的弊端？
**背诵**：① 长事务持有锁时间长，锁冲突、死锁概率大，并发度骤降；② undo log 版本链不能被清理（purge 线程要保留长事务可见的旧版本），导致 undo 表空间膨胀；③ 占用数据库连接不释放；④ 主从延迟加剧（大事务 binlog 大，从库回放慢）；⑤ 一旦回滚代价巨大。建议：大事务拆小，非必要操作移出事务。
## 80+. RR 场景分析题：事务 A 两次查询之间，事务 B 插入并提交，A 会看到吗？
**背诵**：分情况：① A 两次都是快照读（普通 SELECT）→ 看不到 B 插入的行（复用同一个 Read View）；② A 第二次是当前读（FOR UPDATE/UPDATE）→ 能看到（当前读读最新已提交数据）；③ A 先 UPDATE 了 B 插入的行再快照读 → 能看到（该行 trx_id 被改为 A 自己，对自己可见）——这就是 RR 下幻读的典型场景。
## 80++. Buffer Pool 是什么？有什么作用？
**背诵**：Buffer Pool 是 InnoDB 的内存缓冲池（默认 128MB，生产建议设为物理内存的 50%~70%），缓存数据页和索引页。读：先查 Buffer Pool，命中直接返回，未命中读磁盘并加载；写：先改 Buffer Pool 中的页（变脏页），后台线程异步刷盘——把随机磁盘 IO 转为内存操作 + 顺序 redo log，大幅提升性能。配合 WAL，崩溃后通过 redo log 恢复脏页。
## 80+++. change buffer 是什么？
**背诵**：change buffer 是 Buffer Pool 的一部分，缓存对「非唯一二级索引」的修改：当更新的索引页不在内存时，先把修改记在 change buffer，下次该页被读入内存时再合并（merge），避免更新时的随机磁盘读。唯一索引不能用（必须读页检查唯一性）。所以写多读少的表，普通索引更新性能优于唯一索引。
# 六、锁
## 81. MySQL 锁的分类（重要）
**背诵**：按粒度分：全局锁（FTWRL，全库只读，用于逻辑备份）、表级锁（表锁、元数据锁 MDL、意向锁、AUTO-INC 锁）、行级锁（记录锁 Record Lock、间隙锁 Gap Lock、临键锁 Next-Key Lock、插入意向锁）。按模式分：共享锁 S（读锁，可共享）、排他锁 X（写锁，互斥）。按思想分：乐观锁（CAS/版本号，应用层实现）、悲观锁（数据库锁）。
## 82. MySQL 怎么实现乐观锁？（重要）
**背诵**：乐观锁不是数据库内置的，是应用层方案：表里加 version 字段，更新时 `UPDATE t SET data=?, version=version+1 WHERE id=? AND version=旧值`，影响行数为 0 说明被改过，重试。也可以用时间戳或 CAS 思想。适合读多写少、冲突少的场景；冲突频繁时重试成本高，不如悲观锁。
## 83. 在线修改表结构（DDL）会发生什么？
**背诵**：会加元数据锁（MDL 写锁），与所有读写事务互斥。如果表上有未提交的长事务，DDL 会等待，且后续所有对该表的查询都排队等 MDL → 连接打满、服务雪崩。MySQL 8.0 支持部分 DDL 的 INSTANT 算法（秒级加列）；大表改结构推荐用 gh-ost / pt-online-schema-change 在线改表工具。
## 84. 创建索引会锁表吗？
**背诵**：MySQL 5.6+ 的 Online DDL，创建索引用 INPLACE 算法，期间允许读写（不锁表），只在开始和结束阶段短暂持有 MDL 写锁。但 5.6 之前或大表用 COPY 算法会锁表。生产环境大表建索引仍建议低峰期或用 gh-ost。
## 85. InnoDB 行级锁有哪些？（重要）
**背诵**：① 记录锁（Record Lock）：锁单行索引记录；② 间隙锁（Gap Lock）：锁索引记录之间的开区间，防止插入，解决幻读，RR 级别才有；③ 临键锁（Next-Key Lock）：记录锁+间隙锁，锁左开右闭区间，是 RR 下行锁的默认单位；④ 插入意向锁（Insert Intention Lock）：插入时等待间隙锁释放的特殊间隙锁。注意：行锁锁的是索引记录，不是物理行；没走索引的更新会锁全表（所有记录+间隙）。
**图解**（索引记录为 5、10、15、20，RR 级别）：
```
索引记录:    5        10        15        20
           │←间隙→│←间隙→│←间隙→│
记录锁:     [5]      [10]      [15]      [20]     锁单行
间隙锁:        (5,10)  或  (10,15)  开区间        锁区间不锁行
临键锁:     (5,10]    或   (10,15]  左开右闭      锁区间+右行

例：UPDATE ... WHERE id=10 → 加临键锁 (5,10]
   其他事务插入 id=7 会阻塞（落入间隙），更新 id=10 也阻塞
```
## 86. 间隙锁的工作原理？
**背诵**：间隙锁锁的是索引记录之间的开区间 (a, b)，阻止其他事务在间隙中插入新记录，用于 RR 级别防止幻读。间隙锁之间不互斥（多个事务可同时持有同一间隙的 gap lock），只与插入意向锁冲突。RC 级别下间隙锁基本不生效。
## 87. UPDATE 不带 where 条件，加什么锁？
**背诵**：全表所有记录加临键锁（所有行 + 所有间隙），相当于锁全表，且是全表扫描。生产环境绝对禁止。
## 88. UPDATE 带 where 但没命中索引，加什么锁？
**背诵**：无法利用索引定位记录，只能全表扫描，对所有记录加临键锁（相当于锁全表）。所以 UPDATE/DELETE 一定要走索引。
## 89. 两条更新语句更新同一条记录，加什么锁？
**背诵**：排他行锁（记录锁 X 锁）。第一条 UPDATE 先加 X 锁，第二条阻塞等待，直到第一个事务提交或回滚释放锁。
## 90. 两条更新语句更新同一行记录的不同字段，加什么锁？
**背诵**：还是行级排他锁（X 锁），锁的是整行记录而不是字段，所以第二条仍然阻塞。InnoDB 没有字段级锁。
## 91. 了解 MySQL 死锁吗？
**背诵**：死锁是两个及以上事务互相持有对方需要的锁并等待，形成循环等待。InnoDB 有死锁检测（wait-for graph 发现环即触发），检测到后回滚 undo 量最小的事务；也可以设置 innodb_lock_wait_timeout（默认 50s）超时回滚。
## 92. 怎么排查死锁？
**背诵**：① `SHOW ENGINE INNODB STATUS` 查看 LATEST DETECTED DEADLOCK 段，含事务、SQL、持有的锁和等待的锁；② 开启 innodb_print_all_deadlocks 把死锁日志打到错误日志；③ MySQL 8.0 查 performance_schema.data_locks 和 data_lock_waits 表；④ 分析加锁顺序，定位业务代码。
## 93. 怎么避免死锁？
**背诵**：① 固定加锁顺序（所有事务按相同顺序访问表和行）；② 大事务拆小，缩短持锁时间；③ UPDATE/DELETE 走索引，避免锁全表；④ 降低隔离级别（RR→RC，间隙锁失效）；⑤ 减少锁粒度，能用行锁不用表锁；⑥ 合理设置锁超时时间。
# 七、日志
## 94. MySQL 三大日志？（重要）
**背诵**：① undo log（回滚日志）：记录修改前的旧值，用于事务回滚和 MVCC 版本链，保证原子性；② redo log（重做日志）：记录物理页的修改，WAL 先写日志再刷盘，用于崩溃恢复，保证持久性，是 InnoDB 引擎层日志；③ binlog（归档日志）：Server 层日志，记录逻辑 SQL 或行变更，用于主从复制和数据恢复（备份+增量）。
## 95. redo log 和 binlog 的区别和应用场景？
**背诵**：① 层次：redo log 是 InnoDB 引擎层，binlog 是 Server 层，所有引擎通用；② 内容：redo log 是物理日志（某页某偏移做了什么修改），binlog 是逻辑日志（SQL 或行变更）；③ 写入方式：redo log 循环写（固定大小，写满覆盖），binlog 追加写；④ 用途：redo log 用于崩溃恢复，binlog 用于主从复制和时间点恢复。
## 96. redo log 和 binlog 在恢复数据库上有什么区别？
**背诵**：redo log 恢复的是「已提交但数据页未刷盘」的事务，保证 InnoDB 自身崩溃不丢数据，是内存级恢复；binlog 用于「误删库/误删表」后的时间点恢复（全量备份 + 重放 binlog 增量），以及主从复制。redo log 循环覆盖不能用于归档恢复，binlog 持久保留可以。
## 97. 为什么崩溃恢复不用 binlog 而用 redo log？
**背诵**：① binlog 是 Server 层逻辑日志，无法判断哪些数据页已刷盘，重放可能导致已刷盘的页被重复修改；② redo log 是物理日志且幂等（记录页的修改，配合 LSN 可判断页是否已应用）；③ redo log 顺序写小文件性能高，binlog 刷盘策略不同。简单说：redo log 知道"哪些修改还没落盘"，binlog 不知道。
## 98. binlog 的三种格式？
**背诵**：① statement：记录原始 SQL，日志量小，但主从执行环境不同可能导致不一致（如 now()、uuid()）；② row：记录每行数据的前后变更，主从一致性好，但日志量大；③ mixed：混合模式，默认 statement，可能引起不一致时自动切 row。生产推荐 row。
## 99. redo log 怎么实现持久化的？
**背诵**：WAL（Write-Ahead Logging）：事务提交时先把修改写入 redo log buffer → 按刷盘策略写到 redo log 文件（ib_logfile）→ 提交成功返回；数据页由后台线程异步刷盘。崩溃后用 redo log 重放恢复。redo log 是顺序写（比数据页随机写快得多），这就是"先写日志"的性能优势。
## 100. redo log 除了崩溃恢复还有什么作用？
**背诵**：① 将随机写转为顺序写，提升写性能（WAL）；② 配合 Buffer Pool 实现延迟刷盘，减少 IO；③ 是实现两阶段提交（与 binlog）保证主从一致的基础。
## 101. 为什么需要两阶段提交？
**背诵**：保证 redo log 和 binlog 的一致性。如果先写 redo log 后写 binlog 期间崩溃：redo log 有记录但 binlog 没有 → 主库数据正常，从库（靠 binlog 复制）丢数据。反之先写 binlog 崩溃：从库多了主库没有的数据。两阶段提交让两份日志要么都成功要么都失败。
## 102. 两阶段提交的过程？
**背诵**：① 准备阶段（prepare）：InnoDB 把事务 redo log 写入并刷盘，标记为 prepare 状态；② 提交阶段（commit）：Server 层写 binlog 并刷盘，然后 InnoDB 把 redo log 标记为 commit。崩溃恢复时：redo log 处于 prepare 且 binlog 完整 → 继续提交；binlog 不完整 → 回滚事务。
**图解**：
```
时刻    InnoDB(redo log)        Server(binlog)
 T1     写入 prepare ─────────→
 T2     （刷盘）
 T3                          ←── 写入 binlog
 T4                          （刷盘）
 T5     写入 commit ─────────→

崩溃分析：
 T1~T3 间崩溃：redo 是 prepare 但 binlog 没有 → 回滚（两边都没有，一致）
 T4~T5 间崩溃：redo 是 prepare 但 binlog 完整 → 继续提交（两边都有，一致）
```
## 103. redo log 刷盘策略有哪三种？
**背诵**：由 innodb_flush_log_at_trx_commit 控制：0 = 每秒把 redo log buffer 刷盘一次，提交不刷盘，可能丢 1 秒数据，性能最好；1 = 每次事务提交都刷盘（默认），最安全，性能最差；2 = 每次提交写到 OS page cache，每秒刷盘，MySQL 崩溃不丢、机器宕机丢 1 秒。生产常用 1（强一致）或 2（性能折中）。
# 八、性能调优（重要）
## 104. 怎么查看一条语句是否走了索引？
**背诵**：用 EXPLAIN（或 EXPLAIN ANALYZE）查看执行计划，重点看：type（访问类型，从好到差：system > const > eq_ref > ref > range > index > ALL，至少要到 range）、key（实际使用的索引，NULL 表示没走索引）、rows（预估扫描行数）、Extra（额外信息）。
## 105. Extra 中 Using index 和 Using where 的区别？
**背诵**：Using index = 覆盖索引，查询字段都在索引中，无需回表，最优；Using where = 存储引擎返回数据后在 server 层做了 where 过滤（说明有字段没法用索引过滤）；Using index condition = 索引下推，在引擎层用索引条件过滤；Using filesort / Using temporary = 需要额外排序/临时表，要优化。
## 106. 怎么找到慢 SQL？
**背诵**：① 开启慢查询日志（slow_query_log=1，long_query_time 设阈值如 1s），用 mysqldumpslow 或 pt-query-digest 分析；② `SHOW PROCESSLIST` 看当前正在执行的慢语句；③ performance_schema 的 events_statements 统计；④ 接入监控（Prometheus + 慢日志采集告警）。
## 107. 如何优化慢 SQL？
**背诵**：① EXPLAIN 分析执行计划，确认是否走索引、扫描行数；② 没走索引 → 建合适索引或改写 SQL（消除函数、隐式转换、前导 %）；③ 回表多 → 覆盖索引；④ 排序慢 → 利用索引有序性避免 filesort；⑤ 深分页 → 延迟关联/游标；⑥ join 慢 → 小表驱动大表、被驱动表关联字段建索引；⑦ 数据量太大 → 分库分表、归档历史数据。
## 108. 深分页场景如何优化？
**背诵**：问题：`LIMIT 1000000, 10` 要扫描前 100 万行再丢弃，慢。优化：① 游标/滚动查询：`WHERE id > 上一页最大id ORDER BY id LIMIT 10`，利用主键索引直接定位；② 延迟关联：`SELECT * FROM t JOIN (SELECT id FROM t ORDER BY id LIMIT 1000000,10) tmp USING(id)`，子查询走覆盖索引只回表 10 次；③ 业务限制：不允许跳页（如谷歌只给前几十页）。
## 109. SQL 和索引都没问题，查询还是很慢怎么办？
**背诵**：① 看是不是锁等待（行锁/MDL 锁，查 information_schema.innodb_trx）；② Buffer Pool 命中率低，数据页不在内存要读磁盘；③ 机器资源瓶颈（CPU、IO、网络）；④ 主从延迟导致从库读到旧执行计划或统计信息过期 → ANALYZE TABLE；⑤ 大事务/长查询抢占资源；⑥ 数据量达到单机极限 → 分库分表。
# 九、数据库选型
## 110. SQL 和 NoSQL 的区别？
**背诵**：① 数据模型：SQL 是结构化表格、强 schema；NoSQL 是 KV/文档/列族/图，schema 灵活；② 事务：SQL 支持 ACID 事务；NoSQL 大多只保证最终一致（BASE）；③ 扩展：SQL 垂直扩展为主（分库分表复杂）；NoSQL 天然水平扩展；④ 查询：SQL 支持复杂 join 和聚合；NoSQL 查询能力弱但单点读写快；⑤ 场景：SQL 适合强一致、复杂查询（交易、订单）；NoSQL 适合高并发、海量、schema 多变（缓存、日志、社交）。
## 111. MySQL 和 MongoDB 怎么选型？
**背诵**：选 MySQL：需要事务（订单、支付）、复杂关联查询、强一致性、数据结构稳定。选 MongoDB：数据结构多变（文档模型，字段随时加）、写入量巨大（日志、IoT）、需要水平扩展分片、对事务要求低（4.0+ 也支持多文档事务但性能有损耗）。
# 十、高可用
## 112. MySQL 主从复制的过程？
**背诵**：① 主库把变更写入 binlog；② 从库 IO 线程连接主库，拉取 binlog 写到本地 relay log（中继日志）；③ 从库 SQL 线程（5.6+ 可多线程并行）读取 relay log 重放，应用到从库。基于 binlog 的异步复制是默认模式。
**图解**：
```
主库 Master                     从库 Slave
┌──────────┐    binlog    ┌──────────────┐
│ 事务提交   │ ──────────→ │ IO 线程       │
│ 写 binlog │             │   ▼          │
└──────────┘             │ 写 relay log  │
                          │   ▼          │
                          │ SQL 线程      │
                          │ 重放 relay log│
                          │   ▼          │
                          │ 应用到从库     │
                          └──────────────┘
异步模式：主库提交即返回，不等从库 → 可能丢数据
半同步：主库至少等 1 个从库收到 relay log 才返回
```
## 113. MySQL 有几种复制模式？默认是哪种？
**背诵**：① 异步复制（默认）：主库提交即返回，不等从库，可能丢数据；② 半同步复制（semi-sync）：主库至少等一个从库收到 binlog（写 relay log）才返回，兼顾性能和可靠；③ 全同步复制（组复制 MGR / Galera）：所有节点都确认才返回，强一致但性能差。
## 114. 主从复制延迟怎么解决？
**背诵**：① 从库开启并行复制（5.6 库级并行，5.7 组提交逻辑时钟并行，8.0 WRITESET 并行）；② 大事务拆小；③ 半同步复制减少丢数据（不解决延迟）；④ 业务上对实时性要求高的读走主库；⑤ 升级硬件、从库关闭不必要的日志；⑥ 监控 Seconds_Behind_Master 告警。
## 115. 读写分离怎么实现？
**背诵**：① 应用层：代码里区分读写数据源（如 Spring AbstractRoutingDataSource + AOP）；② 中间件：MyCat、ShardingSphere-Proxy、MySQL Router 自动路由；③ 注意主从延迟问题：刚写完马上读可能读不到，方案有强制走主库、延迟等待、GTID 一致性读。
## 116. MySQL 主库挂了怎么办？
**背诵**：① 手动切换：选最新从库升主，其他从库重新指向，应用改配置；② 自动故障转移：MHA、Orchestrator、keepalived+VIP；③ 云 RDS 自带高可用秒级切换；④ 强一致方案：MGR 组复制自动选主；⑤ 注意脑裂问题（双主写冲突），用 fencing 机制避免。
## 117. 什么是分库分表？什么时候分表？什么时候分库？
**背诵**：分库分表是把数据拆到多个库/表。垂直分表：按列拆（大字段、冷热分离）；水平分表：按行拆（单表数据量大，建议单表 500 万~2000 万行或单表超 2GB 考虑分表）；垂直分库：按业务拆（订单库、用户库）；水平分库：同结构数据按规则（user_id 哈希/范围）拆到多库——单库连接数、QPS 到瓶颈时做。
## 118. 分库分表后产生什么问题？怎么解决？
**背诵**：① 分布式事务：跨库事务用最终一致（本地消息表、MQ 事务消息、Seata）；② 跨库 join：禁止，改冗余字段、应用层组装、宽表/ES；③ 全局唯一 ID：雪花算法、号段模式、Redis 自增；④ 分页排序：各分片查询后内存归并，或 ES 兜底；⑤ 扩容迁移：一致性哈希、双写迁移；⑥ 路由：客户端分片（ShardingSphere-JDBC）或代理分片（MyCat）。
# 附录：高频核心问题速记
**索引**：B+ 树（矮胖、叶子链表、IO 少）→ 聚簇索引存整行、二级索引存主键 → 回表 → 覆盖索引避免回表 → 最左前缀 → 索引下推 → 索引失效（函数/隐式转换/前导%/跳过左列）。
**事务**：ACID → 隔离级别 RU/RC/RR/串行化 → RR 默认 → MVCC（隐藏列 + undo 版本链 + Read View）→ RC 每条语句建 Read View，RR 事务级复用 → 幻读：快照读靠 MVCC，当前读靠临键锁，RR 未完全解决。
**锁**：全局锁/表锁(MDL)/行锁 → 记录锁/间隙锁/临键锁 → 无索引更新锁全表 → 死锁检测与排查。
**日志**：undo（原子性+MVCC）、redo（持久性，WAL，崩溃恢复）、binlog（复制+归档）→ 两阶段提交保证 redo/binlog 一致。
**调优**：EXPLAIN（type/key/rows/Extra）→ 慢查询日志 → 覆盖索引/最左前缀/深分页优化。
**高可用**：主从复制（binlog→relay log→重放）→ 异步/半同步/组复制 → 读写分离 → 分库分表（问题：分布式事务、全局 ID、跨库 join）。
