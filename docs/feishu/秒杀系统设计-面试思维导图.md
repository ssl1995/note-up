# 第一部分：面试怎么答（开口框架）
## 一、秒杀场景的特点（先破题）
秒杀的核心特征是"**三高一短**"：
1. **高并发**：瞬时 QPS 可达 10W+，远超日常流量
2. **高竞争**：商品库存极少（如 100 件），大量请求注定失败
3. **高一致性要求**：不允许超卖（库存为负）和重复下单
4. **时间窗口极短**：活动通常只开放几秒到几分钟
一句话总结：**用有限资源服务海量请求，且必须保证公平性与数据正确性。**
也可以用三个字概括设计目标：**稳、准、快**
- **稳**：高可用，流量符合预期要稳定，超出预期也不能掉链子
- **准**：秒杀 10 台就只能成交 10 台，多一台少一台都不行
- **快**：性能足够高，整个请求链路协同优化
## 二、核心矛盾与设计哲学
**核心矛盾**：高并发流量 vs 低库存资源
**设计哲学**（16 字）：**层层过滤、异步解耦、缓存前置、最终一致**
核心思路是"**漏斗模型**"——流量从大到小，层层拦截，最后只有少数请求能到达数据库：
```
10万用户请求
    ↓
【第一层】前端限流 + 静态化（拦住 80%）
    ↓
2万请求
    ↓
【第二层】网关限流 + 防刷（再拦一部分）
    ↓
【第三层】Redis 预减库存（拦住 90%，售罄即拒）
    ↓
2000请求
    ↓
【第四层】消息队列异步处理（削峰填谷）
    ↓
200请求
    ↓
【第五层】数据库最终扣减（安全落地）
    ↓
100个成功订单
```
**为什么这样设计？** 每一层都在做一件事：**尽早拒绝无效请求，保护后端资源。**
## 三、面试回答模板（6 步结构）
面试官问"怎么设计秒杀系统"，按下面 6 步结构化回答：
**第一步：请求入口限流**
- Nginx 限流 + 接入层限流（漏桶、令牌桶算法）
- 黑名单机制拦截恶意 IP/UID
- 早期拦截减轻下游压力
**第二步：页面静态化 + CDN**
- 秒杀页面提前静态化（HTML + JS），通过 CDN 加速分发
- 按钮置灰 + 倒计时，未到时间禁止点击
- 减少动态渲染压力
**第三步：Redis 预减库存（防超卖核心）**
- 活动开始前将库存预热到 Redis
- 用 Lua 脚本保证"查库存 + 扣库存"原子性
- Redis 库存 ≤ 0 立刻拒绝请求
**第四步：异步排队 + 削峰**
- 秒杀成功 → 发消息到 MQ（Kafka/RocketMQ）
- 后端异步消费下单请求
- DB 压力从 10W QPS 降至几千
**第五步：数据库幂等落库**
- MQ 消费者异步写订单入库
- 条件更新防超卖：`UPDATE ... SET stock = stock - 1 WHERE stock >= 1`（原子操作，影响行数为 0 即售罄）
- 唯一索引/状态机保证幂等，防重复下单
**第六步：异步通知 + 支付对接 + 兜底**
- 下单成功异步通知用户，接入支付系统
- 超时未支付 → 定时任务关单退库存
- 监控告警 + 降级预案兜底
### ❌ 错误示范（背书型）
> "我会用 Redis 做缓存，用 RocketMQ 做异步，用 MySQL 存数据，用 Nginx 做负载均衡..."
面试官内心 OS：背挺熟，然后呢？
### ✅ 正确示范（思考型）
> "设计秒杀系统，我认为核心是解决**高并发和低库存的矛盾**。我会从几个层面考虑：
>
> 第一，整体思路是'漏斗模型'，层层过滤流量，每一层尽早拒绝无效请求；
>
> 第二，关键技术点有三个：Redis 预减库存把 DB 压力降到最小、消息队列异步削峰、数据库条件更新防超卖保证一致性；
>
> 第三，业务层面防护不能少：验证码防刷、IP 限流、限购，成本低但效果好；
>
> 最后，一定要有兜底方案：降级、熔断、监控，系统不崩比功能完美更重要。"
## 四、面试回答技巧
1. **先全局后细节**：先描述整体架构，再说核心模块设计
2. **层次分明**：核心问题 → 快速策略 → 弊端 → 优化方案
3. **用数字说明**：QPS、库存量、缓存命中率等
4. **强调成本权衡**：快速上线 vs 高可用，没有完美的架构，只有合适的架构
5. **主动澄清需求**：拿到题先问——用户量多少？峰值 QPS？一致性要求？面试官没给数字时主动假设："先按峰值 10W QPS、允许秒级最终一致来设计"
## 五、常见追问与应答
**Q：如果 Redis 挂了怎么办？**
> 主从切换 + 持久化。极端情况降级到数据库限流，虽然慢但不会崩。
**Q：如何保证 Redis 和数据库库存一致？**
> 最终一致性。异步同步 + 定时对账（如每分钟比对差值），以数据库为准修正 Redis，异常告警人工介入。
**Q：活动还没开始，Redis 库存就被刷完了怎么办？**
> 服务端校验活动时间，未到时间的请求直接拒绝。
**Q：为什么要用消息队列，直接同步写数据库不行吗？**
> 可以，但抗不住高并发。MQ 核心价值是"削峰"，让数据库平稳接收请求。请求量小（<5k）可以直调，量大必须走 MQ。
**Q：怎么防止重复下单？**
> 三道防线：Redis 记录用户秒杀单号（流程中禁止重复发起）+ 分布式锁 + 数据库唯一索引 (user_id, goods_id) 兜底。
**Q：系统的瓶颈在哪里？流量再大 10 倍怎么应对？**
> 瓶颈通常在数据库写能力和热点行竞争。应对：分库分表（按 user_id 哈希）、热点商品单独拆分、批量处理减少 IO、读写分离、异地多活。
**Q：怎么测试系统并发量？**
> 上线前压测：JMeter/Gatling 模拟 10W 并发，找系统瓶颈；全链路监控 Prometheus + Grafana 观察 QPS、延迟、错误率。
## 六、加分项（高阶）
- **幂等性**：MQ 消费保证幂等，唯一键约束或 Redis SETNX
- **数据一致性**：Redis 与 DB 最终一致，活动结束后对账
- **压测验证**：JMeter 模拟真实流量找水位
- **结合实际案例**："我之前做过 XX 系统，思路类似，QPS 从 X 提升到 Y"
- **缓存三兄弟**：穿透（布隆过滤器）、击穿（热点 key 互斥重建）、雪崩（随机过期时间）
- **隔离设计**：秒杀服务独立部署、独立 Redis 集群，避免拖垮主站

# 第二部分：知识点整理（来自飞书文档）
## 一、核心思路（三大问题）
### 1. 流量控制：削峰 vs 限频
- **削峰**：请求进来就丢消息队列，堆 MQ 机器扛海量请求
  - 缺点：产品体验差，大量用户抢了之后过一会儿都提示抢不到，伤感情
- **限频**：每秒请求超过频率就拒绝
  - 一般放在网关做，用通用限流组件
  - **主流选择，后续讨论以限频为前提**
### 2. 库存扣减：Redis 预扣名额
- MySQL 扛不住高并发，Redis 不够可靠
- 按 10W+ 流量考虑，方案：**Redis 预扣库存**
- Redis 中存放的可以看作"名额"，真正的库存不在这里
### 3. 真实库存：MySQL 强一致兜底
- MySQL 存放真正的库存，保证库存可靠
- MySQL 库存扣减成功 → 创建订单 → 前端跳支付页 → 支付成功更新状态
- 放弃支付的，名额返回，一般 5~10 分钟
## 二、整体架构
### 服务设计
- 接入层服务
- 商品信息服务
- 秒杀信息服务
- 预扣服务
- 库存服务
- 订单服务
### 存储设计
- **Redis 实现预扣，MySQL 是实际库存**
- Redis 只是入场名额，图它快，一般不会出现异常，大多数拿到名额的人都能拿到库存
- 库存最终受强一致的 MySQL 保护；如果出现并发、主从切换等异常，拿到名额的人不一定能拿到库存
- **消息队列（Kafka）**：异步传递消息，也算临时存储
  - 为什么预扣后还要 MQ？虽然到 MySQL 的量已经很小，但如果商品数量超过 1W，秒杀瞬间几百 ms 打到 MySQL 的流量也会将其打崩
### 表结构设计
#### MySQL 库存表 `t_seckill_stock`
| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint(20) | 主键自增 ID |
| goods_id | varchar(256) | 商品 id |
| stock | int(11) | 秒杀活动库存数目 |
#### MySQL 秒杀记录表 `t_seckill_record`
| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint(20) | 主键自增 ID |
| sec_num | varchar(256) | 秒杀编号 |
| order_num | varchar(256) | 订单编号 |
| user_id | varchar(256) | 用户 id |
| goods_id | varchar(256) | 商品 id |
| amount | int(10) | 抢购数量 |
| status | tinyint(4) | 秒杀单据状态（见下方状态机） |
**状态机：**
| 值 | 枚举 | 含义 |
|---|---|---|
| 1 | SK_STATUS_BEFORE_ORDER | 预购抢到名额，待生成订单 |
| 2 | SK_STATUS_BEFORE_PAY | 订单生成之后，待付款 |
| 3 | SK_STATUS_PAYED | 终态，已付款 |
| 4 | SK_STATUS_OOT | 终态，超时未付款 |
| 5 | SK_STATUS_CANCEL | 终态，主动取消 |
#### Redis 结构（3 个核心 Key）
1. **`SK:UserGoodsSecNum:{goodsID}:{userID}`** → value 为 secNum
   - 意义：某用户在某商品的秒杀单号；不为空表示在秒杀流程中，**禁止重复发起**
2. **`SK:Stock:{goodsID}`** → value 为名额数量
   - 例：`SK:Stock:1` = 10 表示 1 号产品还剩 10 个名额
3. **`SK:Limit:{goodsID}`** → value 为全局限额
   - 单个用户对该商品最多能秒杀多少件
4. 补充：**`{secNum}`**（秒杀单号本身作为 Key）→ value 为秒杀记录 JSON
   - 前端轮询秒杀状态时查的就是它

**实际命令示例**（假设用户 userId=10086，商品 goodsId=1，买 2 件，秒杀单号 secNum=abc123）：

```bash
# ===== 活动开始前，运营/系统预热数据 =====
SET SK:Stock:1 100          # 1号商品预热 100 个名额
SET SK:Limit:1 2            # 1号商品每人限购 2 件

# ===== 秒杀时 Lua 脚本内部实际执行的命令 =====
GET SK:UserGoodsSecNum:1:10086        # 查用户是否在秒杀中 → nil（没在秒）
GET SK:Limit:1                        # 查限额 → "2"
GET SK:UserSecKilledNum:10086:1       # 查用户已秒数量 → nil（没秒过）
GET SK:Stock:1                        # 查剩余名额 → "100"

# 校验通过，执行扣减：
DECRBY SK:Stock:1 2                   # 名额 100 → 98
INCRBY SK:UserSecKilledNum:10086:1 2  # 用户已秒数 0 → 2
SET SK:UserGoodsSecNum:1:10086 abc123 # 记录用户正在秒杀的单号
SET abc123 '{"secNum":"abc123","userId":10086,"goodsId":1,"status":1}'  # 存秒杀记录

# ===== 前端轮询秒杀状态 =====
GET abc123   # → 拿到 JSON，status=1 待生成订单；变成 2 待付款时跳支付页
```
**扣减流程要点：**
1. 查看库存：`SK:Stock:{goodsID}` 的数字
2. 扣减库存：`DECR SK:Stock:{goodsID}`
3. 以 secNum 为 Key 记录秒杀信息（secNum 提前用 UUID 生成）
⚠️ **并发问题**：很多请求同时到来，都发现库存 > 0（如库存=1），同时扣减会扣成负数 → **需要 Lua 保证原子性**
### 结合业务的整体流程
1. 拉取基本的商品信息和秒杀信息
2. 发起抢购
   - 2.1 扣减 Redis 名额，并记录秒杀信息（含当前状态）
   - 2.2 丢进 Kafka，异步扣库存和生成订单
3. 消费 Kafka 消息
   - 3.1 扣减 MySQL 库存
   - 3.2 通过订单系统创建订单
   - 3.3 将秒杀记录写入 `t_seckill_record` 表
   - 3.4 更新预扣系统中 Redis 秒杀信息状态 → 前端可跳转支付页
4. 支付完成 → MySQL 状态更新为已支付
5. 超时未支付 → 定时任务扫描，更新为超时未支付
## 三、核心要点
### 1. 限流
- 每秒请求超过频率就拒绝
- 限流可以单独作为一个系统设计，一般放在网关
- 理解为都有通用的限流组件即可
### 2. 限购逻辑
**Redis 层实现：**
1. 查询商品限额
2. 查询用户针对这个商品已经秒杀了几个
3. 想买的个数 + 用户已买的数量，和商品限额比较
```lua
-- 判断这个用户是不是已经超过限额了
local limit = redis.call('get', keyLimit)
local userSecKilledNum = redis.call('get', keyUserSecKilledNum)
if limit and userSecKilledNum and tonumber(userSecKilledNum) + tonumber(num) > tonumber(limit) then
   retAry[1] = -2
   return retAry
end
```
**限购风险与 MySQL 兜底：**
- Redis 做限购可能靠不住，最后要用 MySQL 兜底
- 引入限购表配置限购信息
- 流程：
  1. 查询用户当前限购情况
  2. 没有限购额度 → 拒绝
  3. 在限购额度以内 → 扣减额度，并增加用户购买数量记录
### 3. 前端状态查询
- 问题：前端怎么查询秒杀状态？→ 在 Redis 中单独记录
- 调用秒杀接口后得到 secNum（秒杀单号），通过单号查询对应数据
```go
type PreSecKillRecord struct {
    SecNum     string // key
    UserID     int64
    GoodsID    int64
    OrderNum   string
    Price      float64
    Status     int
    CreateTime time.Time
    ModifyTime time.Time
}
```
### 4. 预扣库存（扣减名额）—— Lua 脚本 ⭐
**提炼：**
1. 使用 Redis 的高性能管理名额
2. Redis + Lua 保证原子性
3. 增加限额和状态记录逻辑
**5 个参数：**
- key1：用户 id
- key2：商品 id
- key3：希望抢购多少个名额
- key4：秒杀单号（唯一标识）
- key5：秒杀记录（以秒杀单号为 Key 的 JSON 数据）
**Lua 脚本四步（附 Java 对照注释）：**

先理解 Lua 与 Java 的语法对照：

| Lua | Java 对应 | 说明 |
|---|---|---|
| `local x = ...` | `String x = ...` | 声明局部变量 |
| `..` | `+`（字符串拼接） | `"SK:Stock:" .. id` 即 `"SK:Stock:" + id` |
| `redis.call('get', k)` | `jedis.get(k)` | 调用 Redis 命令 |
| `nil` | `null` | 空值 |
| `~=` | `!=` | 不等于 |
| `tonumber(x)` | `Long.parseLong(x)` | 字符串转数字 |
| `--` | `//` | 单行注释 |
| `KEYS[1]` | 入参数组第 1 个 | Lua 数组从 1 开始 |

```lua
-- ===== 关键 Key 定义（KEYS 是调用方传入的参数数组，下标从 1 开始）=====
-- KEYS[1]=用户id  KEYS[2]=商品id  KEYS[3]=抢购数量  KEYS[4]=秒杀单号  KEYS[5]=秒杀记录JSON
-- 相当于 Java: String keyLimit = "SK:Limit:" + goodsId;
local keyLimit = "SK:Limit:" .. KEYS[2]
-- 用户在该商品下的秒杀单号 Key，如 SK:UserGoodsSecNum:1:10086
local keyUserGoodsSecNum = "SK:UserGoodsSecNum:" .. KEYS[2] .. ":" .. KEYS[1]
-- 用户在该商品下已秒杀数量 Key，如 SK:UserSecKilledNum:10086:1
local keyUserSecKilledNum = "SK:UserSecKilledNum:" .. KEYS[1] .. ":" .. KEYS[2]

-- ① 判断用户是否在秒杀中（防重复提交），是则直接返回已有 secNum
-- 相当于: String alreadySecNum = jedis.get(keyUserGoodsSecNum);
local alreadySecNum = redis.call('get', keyUserGoodsSecNum)
-- 返回数组初始化：{错误码, 秒杀单号}，0 表示成功
local retAry = {0, ""}
-- 如果已存在秒杀单号（非空），说明正在秒杀流程中
if alreadySecNum and string.len(alreadySecNum) ~= 0 then
   retAry[1] = -1              -- 错误码 -1：重复秒杀
   retAry[2] = alreadySecNum   -- 把已有的秒杀单号返回给前端继续轮询
   return retAry
end

-- ② 判断用户是否超过限购额度
local num = KEYS[3]                                        -- 本次想买几件
local limit = redis.call('get', keyLimit)                  -- 该商品每人限购数
local userSecKilledNum = redis.call('get', keyUserSecKilledNum) -- 用户已秒到几件
-- 已秒数量 + 本次想买数量 > 限额 → 拒绝
if limit and userSecKilledNum and tonumber(userSecKilledNum) + tonumber(num) > tonumber(limit) then
   retAry[1] = -2   -- 错误码 -2：超过限购
   return retAry
end

-- ③ 判断活动名额是否还够
local stockKey = "SK:Stock:" .. KEYS[2]        -- 名额 Key，如 SK:Stock:1
local stock = redis.call('get', stockKey)
-- 名额不存在 或 剩余名额 < 想买数量 → 拒绝
if not stock or tonumber(stock) < tonumber(KEYS[3]) then
   retAry[1] = -3   -- 错误码 -3：名额不足（已抢完）
   return retAry
end

-- ④ 校验全部通过，执行扣减（这 4 条命令与上面的判断在同一个 Lua 里，整体原子执行）
redis.call('decrby', stockKey, KEYS[3])            -- 名额 -N，如 100 → 98
redis.call('incrby', keyUserSecKilledNum, KEYS[3]) -- 用户已秒数 +N
redis.call('set', keyUserGoodsSecNum, KEYS[4])     -- 记录用户↔秒杀单号映射（防重复）
redis.call('set', KEYS[4], KEYS[5])                -- 以秒杀单号为 Key 存秒杀记录 JSON
return retAry   -- 返回 {0, ""} 表示成功
```

**关键点：以上整个脚本在 Redis 中是原子执行的**——相当于 Java 里把 ①②③④ 全部放进一个 `synchronized` 块，但比 Java 锁快得多，因为 Redis 单线程执行 Lua，期间不会插入其他请求，所以"查库存→扣库存"之间绝不会被插队，从根上杜绝超卖。

**Java 侧调用方式（Jedis）：**

```java
// Java 代码只需要把脚本和参数传给 Redis 即可
String luaScript = "..."; // 上面的脚本
List<String> keys = Arrays.asList(
    "10086",   // KEYS[1] 用户id
    "1",       // KEYS[2] 商品id
    "2",       // KEYS[3] 抢购数量
    "abc123",  // KEYS[4] 秒杀单号（提前 UUID 生成）
    jsonRecord // KEYS[5] 秒杀记录 JSON
);
// eval 执行脚本，返回 Lua 的 return 值
List<Object> result = (List<Object>) jedis.eval(luaScript, keys, Collections.emptyList());
long code = (Long) result.get(0); // 0=成功 -1=秒杀中 -2=超限购 -3=已抢完
```
### 5. 扣减后怎么传递给库存服务
- 不是直接调用库存服务打 MySQL，要**分情况**：
- 商品秒杀总数一般很少（几百、几千），大部分流量没抢到名额，只有商品数量的请求打到 MySQL，问题不大
- 但如果商品数量是 2W，一瞬间秒完打到 MySQL 就扛不住了
- **结论：**
  - 请求量 < 5k：直接扔过来，MySQL 扛得住
  - 否则：扔消息队列异步消费，MQ 起削峰作用
### 6. 生成订单、扣减库存（MySQL 侧）
**MySQL 涉及两部分数据：**
1. 库存：商品 id、库存总数、库存数量 stock
2. 操作记录：唯一 id（用户 id + 商品 id）、订单状态（等待支付/订单关闭/支付成功）、用户 id、商品 id、抢购数量
**消费 MQ 数据的 5 个步骤：**
1. 扣减数据库库存
2. 产生真正的订单（专门订单系统，订单有状态）
3. 在 `t_seckill_record` 表产生订单记录，记录状态，支持幂等
4. 通知预扣系统更新 Redis 状态；发现数据异常此时做修复；前端发现 Redis 状态变了可跳转付费页
5. 付费后状态改变；超时未付费，额度退回
**MySQL 不超卖原理：**
```sql
-- ① 扣库存
UPDATE t_seckill_stock SET stock = stock - 1
WHERE stock >= 1 AND product_id = xxx;
-- 影响行数为 0 → 库存已扣完，不再执行②，通知 Redis 已抢完

-- ② 插入秒杀记录
INSERT INTO t_seckill_record(order_id, user_id, goods_id, status)
VALUES (...);  -- status = 待付款
```
### 7. 退回逻辑
#### A. 名额加载回 Redis（防少卖）
- 场景：MySQL 库存还存在，且 Redis 名额已为 0 → 可能少卖了
- 保护：为避免还有请求在处理中，状态维持超过 x 分钟（如 5 分钟）再处理，分钟级时间足够消息处理
- 动作：确定少卖后，把 MySQL 库存加载到 Redis
#### B. 超时库存退回 MySQL
- 定时任务扫描：订单超时未支付 → 额度加载回 MySQL
- **乐观锁 + 事务实现幂等**
- 由于支付超时已过去很长时间，大概率 Redis 名额早没有了，可主动触发一次名额加载逻辑
- 也可以简单点：更新 MySQL 额度后直接加载 Redis，失败了还有名额加载逻辑兜底
**退还 MySQL 额度操作：**
```sql
-- 通过记录状态做幂等，where status 条件乐观锁保护
UPDATE t_seckill_record SET status = 超时关闭
WHERE order_id = xxx AND status = 待支付;
-- 影响行数不为 0 → 继续退还库存

UPDATE t_seckill_stock SET stock = stock + 2
WHERE product_id = xxx;
-- 注意：以一次买 2 个为例，买 10 个就是 stock + 10
```
## 四、反黄牛策略
### 1. 限购
- 基础保障，保证货品不被黄牛占据太多
### 2. 用户级频控
- 黄牛大多用代码抢购，点击速度比人快得多，导致竞争不公平
- 某用户请求接口次数过于频繁 → 一般是脚本 → 只针对该用户做限制
### 3. IP 限制
- 常见做法，但容易误杀：同一网络的用户可能是同一个出口 IP
- 阈值不能太低，更多用来兜底
### 4. 验证码（更优方案）
- **91 原则**：90% 的时间都用在验证码输入上，脚本点击的影响降到很低
- 另一个好处：把用户高度集中的点击在物理上打散成好几秒（大家答题时间不一样），起到流量错峰作用
- 缺点：降低用户体验，天猫、京东很少用这种方式
- **没有银弹**
### 5. CDN
- 静态资源放到 CDN 上，对后端没啥好说的，为了完整性提一下

# 第三部分：一句话速记
```
秒杀系统设计 = 漏斗模型 + 三层防护 + 兜底方案

漏斗模型：前端 → 网关 → Redis → MQ → 数据库（层层过滤）

三层防护：
  - 技术层：缓存、异步、限流
  - 业务层：验证码、限购、风控
  - 运维层：监控、告警、降级

兜底原则：宁可少卖，不可超卖；宁可降级，不可崩溃
```
